# Milestones can be period-shaped, not just a point

Milestones (`shared-types`' `Milestone`) were always a `PointInTime` (a single `at` date) — reasonable for an invention's first appearance, but wrong for an entity whose own Wikipedia tagline states a range (e.g. Q42005 Black Death, "1346-1353 pandemic in Eurasia and North Africa", stored with only `at: {year: 1346}`). Grilled with the user (grill-with-docs session, 2026-08-12) into the following design:

- **Type**: `Milestone` stays one exported name, but its date shape is now a union (`MilestonePeriod | MilestonePoint`, both unexported) — not a second exported type the way `Conflict`/`ConflictEvent` split. A period-shaped milestone isn't a different *kind* of milestone, just a better-known date; narrowed the same way `ConflictEntry` is, `"period" in entry`, not a `kind` discriminant.
- **Determination**: pipeline-derived, not curator-assigned. `queries/milestones-enrichment.ts` now also fetches `P582` (end time), paired with whatever `?date` the existing `DATE_PROPERTIES` COALESCE resolved — the exact same pattern `conflicts-enrichment.ts` already uses for its own `?endDate` (independent of which property won `?date`, no gating on `P580` specifically having been the winner). A row with a resolved end date becomes period-shaped in `write-datasets.ts`'s `buildMilestones`; a row without one stays point-shaped — the same shape rule `buildConflicts` already applies to `Conflict`/`ConflictEvent`.
- **No validation guard-rail**: no plausibility bound on the resulting period length, and no curator override mechanism. Consistent with how Conflict periods are already trusted as-is (a 116-year Hundred Years' War is accepted at face value) — adding a bespoke check only for Milestones would be an inconsistency, not a safety net.
- **Rendering**: a period-shaped Milestone lands in the Conflicts+Milestones lane's `rangeLayout` bucket and renders with the identical rounded-cap-line treatment a Conflict period gets — no distinct visual style for "this range is an era, not a war." It keeps its own `MILESTONE_CATEGORY_COLORS` category color rather than switching to the flat `CONFLICT_COLOR` — same "color, not shape, tells them apart" rule the lane already used for point markers.

## Consequences

`EnrichedMilestone`/`TaggedMilestone` gain `endYear`/`endMonth`, mirroring `EnrichedConflict`/`TaggedConflict`. No backfill script needed — re-running the Milestones fetch (`npm run fetch -- --lane=milestones`) naturally regenerates `milestones-curated-enriched.raw.json` with `P582` included, and any currently-tracked milestone QID with a resolvable end date (Black Death, COVID-19 pandemic, Great Depression, 1918-1920 flu pandemic, and others found by a rough tagline grep) picks up a period on the next `build-data`/`publish-data` run. `packages/web`'s `map-to-items.ts` (`MilestoneItem` gains `endYear`/`isPoint`, `mapMilestones` narrows the same way `mapConflicts` does) and `ConflictsMilestonesLane.tsx` (range items now carry `fill`/`kind` instead of the hardcoded `CONFLICT_COLOR`/`'conflict'`) follow the same shape rule Conflicts already established, rather than introducing a parallel one.
