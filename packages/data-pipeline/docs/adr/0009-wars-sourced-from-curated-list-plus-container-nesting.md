# Wars & Conflicts sources from a curated QID list plus Wikidata enrichment, with Container/parentId nesting

Wars & Conflicts' original source (`fetch-historical-events.ts`) ran 9 independent per-`ConflictCategory` Wikidata SPARQL scans, one `instance-of` type-claim query per category — the same low-signal, no-real-classification pattern that made Discoveries' original source produce junk top entries before that lane switched to a curated list (ADR 0008). Wars hadn't hit that exact failure mode, but the underlying problem was identical: nobody was choosing which conflicts matter, Wikidata's `instance of` claims were. Separately, umbrella conflicts (a multi-phase campaign containing individual wars, which in turn contain point-in-time events) had no way to be represented — a prior effort removed the one mechanism that gestured at this (`partOfWarName`, a free-text string) because a flat string can't reliably resolve to a real entity.

Wars switched to a checked-in, curator-verified list (`data/raw/wars-curated.raw.json` — `id`/`name`/`category`/optional `parentId` only), backfilled with a batched per-QID SPARQL enrichment pass (`fetch-wars-enrichment.ts`) for `sitelinks`/`wikipediaUrl`/`country`/`image`/`description`/start-and-end dates — the same VALUES-clause pattern `fetch-events-enrichment.ts` uses, extended with the date/description `OPTIONAL` blocks the old per-category query already had. **Diverges from Discoveries' precedent in two ways**: description and dates are Wikidata-enriched here, never curator-authored (Discoveries curates both by hand); and there's no reusable bootstrap/source-merge tooling — the curated list is supplied directly by the curator, one-off, not grown from a scraped source. A **Container** — a curated `War` with no `parentId` — is the top level of an optional, depth-capped (3 levels) nesting relationship that lets an umbrella conflict genuinely contain sub-wars and events as real, independently-curated entities. `parentId` (on both `War` and `WarEvent`, always resolving to another row's `id`, which is always a `War`) is validated at Output (`buildWars`); a violation drops the offending row rather than publishing it.

Consequences: `ConflictCategory` shrank from nine values to six (`battle`/`siege`/`peace-treaty` dropped — inherently sub-events of a war, not standalone conflicts), with `CONFLICT_CATEGORY_COLORS` and `design-tokens.md` updated to match. `War` vs. `WarEvent` shape is now decoupled from both category and curator input — decided at Output purely by what the row's enrichment resolved (both a start and end date → `War`; only one → `WarEvent`; neither → dropped as an enrichment failure), retiring the old `BAR_RENDERED_TYPE_QIDS` category-gated rule entirely. The 9-query scan, its per-category sitelink floors, `event-type-categories.ts`, and `group-rows.ts`'s Wars usage were all removed as dead code once the curated path landed. A live run surfaced a real data-quality issue this design doesn't fully protect against: roughly half the initial hand-off list's Wikidata QIDs pointed to unrelated items (a QID-resolution defect in the list itself, not a Wikidata coverage gap) — caught by an unexpectedly high missing-date rate and fixed by cross-checking every QID's Wikidata label against its curated name, not by anything the pipeline itself validates. A small number of well-known conflicts still resolve no date, or resolve only a point-in-time despite common description text implying a range (e.g. Wikidata models the Russian Revolution as a single 1917 point, not a 1917–1922 span) — an accepted trade-off of sourcing dates from Wikidata's structured claims rather than curator judgment.
