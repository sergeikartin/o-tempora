# AI Workflow Rules

These are rules, not suggestions. Follow them exactly. If a rule and a request conflict, stop and flag the conflict rather than silently picking one.

## Overall Approach

- Before writing any code, read `project-overview.md`, `architecture.md`, and `code-standards.md` in full. They are the spec. Do not rely on a chat summary or your memory of an earlier conversation about this project — the files are the source of truth, and they may have changed since any prior discussion.
- Work spec-first. Before writing code for a unit of work, state in one or two sentences what you are building and which invariant(s) in `architecture.md` apply to it. If you cannot state this, stop and ask before proceeding.
- Work incrementally. Never generate an entire layer, an entire feature, an entire pipeline, or the whole app in one pass. Build one slice at a time — one feature, one widget, one pipeline stage — and stop for review before starting the next.
- Do not build functionality beyond the current unit of work, even if the next piece seems obvious or trivial to add. Flag what you think comes next; do not build it unasked.

## Scoping Rules

- One unit of work per turn. A unit is one feature slice, one widget, one pipeline stage, or one bug fix — not "the filters" (three slices) and not "the timeline" (a widget plus its dependencies).
- No speculative changes. Do not refactor unrelated code, rename files, reorganize folders, or clean up adjacent code unless that is the explicit task. If you notice something that should change, report it in your response — do not fix it silently as a side effect of an unrelated task.
- Do not add a new dependency, library, or tool that isn't already listed in `architecture.md`'s Stack table without calling it out explicitly and pausing for confirmation before installing it.
- Do not cross the mini-FSD layer boundaries (`shared → features → widgets → app`) or reintroduce a dropped layer (`entities`, `pages`) without being explicitly told to. Layer omission was a deliberate project decision, not an oversight to "fix."
- Do not touch `/data-pipeline` while working on `/src`, or the reverse, unless the task explicitly spans both. They are separate projects that communicate only through generated JSON.

## When to Split Work Into Smaller Steps

- If a task would touch more than one FSD layer — for example, a feature's state plus the widget that consumes it — split it into one step per layer, built in dependency order: `shared` → `features` → `widgets` → `app`.
- If a task would add more than roughly 150–200 lines to a single file, stop and propose a smaller decomposition before writing it.
- If a task touches both the frontend and the data pipeline, split it into two units, even if they're logically related — they are still two separate projects.
- If a task requires a new slice, define and confirm that slice's public API (`index.ts`) as its own first step, before filling in internals.

## Handling Missing or Ambiguous Requirements

- If a requirement is missing from `project-overview.md` or `architecture.md`, do not infer it silently and keep going. Either stop and ask, or — only if a reasonable default clearly exists — state the assumption explicitly in your response and in a code comment, then proceed. Never guess without saying so.
- If `project-overview.md`, `architecture.md`, and `code-standards.md` conflict with each other, stop and surface the conflict. Do not silently pick one and act as though there was no conflict.
- Never invent product scope. If a task like "build the filter bar" is ambiguous about what it includes, ask — don't guess based on what seems reasonable.
- If a requirement appears to violate one of the invariants listed in `architecture.md`, stop before writing code. State the conflict directly and ask whether the invariant should change or the request should be reinterpreted. Never silently violate an invariant to satisfy a request.

## Files That Must Not Be Modified Without Explicit Instruction

- `packages/shared-types/src/data/*.json` — machine-generated by the data pipeline's Output stage. Never hand-edit these files. If the data looks wrong, that's a pipeline bug (fix Score or Tag logic and regenerate) — not something to patch in the frontend.
- `data-pipeline/data/raw/` — checked-in raw Wikidata snapshots. Only the Fetch stage may regenerate these. Never hand-edit a raw snapshot to "fix" a bad entry.
- Anything inside `node_modules/` or third-party/vendor code, including vis-timeline's internals. If the library needs different behavior, wrap it in `widgets/timeline-canvas/` — do not patch the library itself.
- A slice's internal files, from outside that slice. Only a slice's `index.ts` public API is a valid import target — never reach into another slice's internal files directly (e.g. `features/filter-by-region/some-internal-file.ts`).
- `architecture.md`, `code-standards.md`, and `project-overview.md` themselves, during implementation work. These are specs to build against. Propose changes to them explicitly, as their own separate step — never rewrite them silently as a side effect of writing code.

## Keeping Documentation in Sync With Implementation

- If implementation reveals that a documented decision is wrong, outdated, or unworkable — for example, a library can't actually do what `architecture.md` assumed — stop coding and propose a specific doc edit before proceeding. Do not code around the discrepancy and leave the docs stale.
- If a new rule emerges during implementation that the codebase must never violate going forward, propose adding it to the Invariants section of `architecture.md` — don't just enforce it in code without documenting it.
- If a unit of work adds, renames, or removes a slice or folder, update `code-standards.md`'s File Organization section in that same unit of work — not as a deferred follow-up.
- If a unit of work adds a new top-level dependency, add a row to `architecture.md`'s Stack table in that same unit of work.

## Verification Checklist Before Moving to the Next Unit

Before treating a unit of work as complete, check every item below and state explicitly, in your response, that you've checked it — don't just assert the unit is "done":

1. FSD layer direction is respected (`shared → features → widgets → app`) — no upward imports, no same-layer-sideways imports.
2. Every date value uses `Temporal.PlainDate`; the only legacy `Date` construction is the single adapter inside `widgets/timeline-canvas`.
3. Filters combine with AND, never OR, per Invariant 2 in `architecture.md`.
4. No runtime code fetches from Wikidata or any external API, per Invariant 6.
5. Nothing outside the pipeline's Output stage writes to `packages/shared-types/src/data/*.json`.
6. Steiger passes with no new violations — actually run it, don't assume it would pass.
7. TypeScript strict mode is clean, with no `any` introduced.
8. If this unit touched file organization or the stack, `code-standards.md` and/or `architecture.md` were updated in this same unit — not deferred.
9. Every invariant in `architecture.md` that applies to this unit has been checked one by one, not assumed satisfied by inspection alone.

If any item fails, fix it before reporting the unit as complete. Do not move to the next unit with a known-failing checklist item.
