# 06 — Fix the CPU-throttled CLS/late-LCP regression from hydration's forced reflow

**What to build:** A fix for the regression [[05-preload-fonts-the-prerendered-viewport-actually-uses]] found, corrected the attribution of, and then confirmed (in that ticket's follow-up comment) is real hardware behavior, not a stress-test artifact: a modest, realistic 2x CPU slowdown alone — no network throttling needed — is enough to reproduce a **CLS of 0.51** and a **render-delay-dominated LCP** (~5s at 2x CPU, ~11s at the original 4x-CPU stress profile) on the prerendered default viewport. Genuinely unthrottled hardware shows neither (CLS 0.00, LCP 2.2s), so this isn't a synthetic-only concern — real mid/low-range mobile visitors will hit it.

`ForcedReflow` names `main-*.js` as the source (~779ms total reflow time at 2x CPU) and `CLSCulprits` can't attribute the shift to any specific node ("No potential root causes identified"), which is itself a clue: the shift isn't one element's late-loading resource, it's layout thrashing from interleaved DOM reads/writes during hydration's first commit.

Two concrete suspects in `TimelineCanvas.tsx`, both worth profiling directly rather than guessing between them:
1. **Initial-viewport-centering**: two sequential `useLayoutEffect`s (around line 546 and line 557) each read `container.clientWidth` and then write state (`setPixelsPerYear`/`setViewportWidthPx` in the first; `syncScrollLeft`/`setScrollLeft` in the second, gated on the first's state actually landing) — a read-write-read-write pattern across two effects/commits is a classic forced-layout setup, especially with ~244 marks in the DOM for the browser to re-lay-out between them.
2. **D3 mark-adoption path** ([[02-d3-join-adoption-logic]]'s `seedPrerenderedData`): adopting ~244 pre-existing prerendered mark nodes per lane may involve per-node reads (e.g. via each mark's `MARK_ID_SELECTOR` child) interleaved with the join's attribute writes.

**Blocked by:** none (05 is done; this starts from its findings).

**Status:** done — CLS reproduces at a deterministic 0.00 (down from 0.51) across repeated fresh-context 2x-CPU trials; see Comments for the full chain of fixes, including the pixelsPerYear/scroll-position fixes that closed the previously-open architectural gap.

- [x] Confirm or rule out each of the two suspects above; there may be others.
- [x] Fix by batching: do all layout reads before any writes in the offending pass (e.g. `requestAnimationFrame`-free read/write separation, or `useLayoutEffect` reads that write only once pixelsPerYear/scrollLeft are both known, rather than in two dependent commits), or otherwise remove the interleaving — not by throttling/deferring the work further, since the initial-viewport-centering values are needed for the very first correct paint after hydration.
- [x] Re-run the same three-point check from 05's follow-up (unthrottled, Fast 4G + 2x CPU, 2x CPU alone) on `dist/` and confirm CLS returns to 0.00 (or is materially reduced) at 2x CPU, with LCP's render-delay subpart correspondingly smaller. — CLS reaches a deterministic 0.00 at 2x CPU (3 fresh-context trials); see Comments for the full chain of fixes that got there.

## Comments

**Profiling.** Built `dist/` with `--sourcemap` into a scratch dir and traced it (mobile 390×844×3, 2x CPU, no network throttle — the realistic profile 05 settled on) via `performance_start_trace` + `ForcedReflow`. The trace tooling's own sourcemap resolution for the two named call frames landed inside `react-dom-client.production.js`/`scheduler.production.js` — a red herring: `source-map-js`'s `originalPositionFor` falls back to the nearest *preceding* mapped segment when a byte range has no mapping of its own, and vendor code's mappings are sparse. Cross-checked instead by searching the bundle's raw text for unique substrings from each suspect (`clientWidth,p?` for effect 1's `defaultPixelsPerYear` call, `timeline-initial-render` for effect 2, `MARK_ID_SELECTOR`'s `.d3-hit` for `seedPrerenderedData`) and comparing their real byte columns against the flagged ones directly — exact match, no ambiguity.

**Suspect 1 confirmed, suspect 2 ruled out.** The flagged columns landed exactly on: TimelineCanvas's own initial-viewport-centering effects (line ~546's `container.clientWidth` read, line ~557's `syncScrollLeft` write immediately followed by a `container.scrollLeft` read-back), plus (unexpectedly) `PeopleLane`'s pin-to-bottom effect (`el.scrollTop = el.scrollHeight`) and the pan-tracking scroll-listener's mount. `seedPrerenderedData`'s code (`.d3-hit`/`data-entity-id` reads) lives ~20,000 bundle-columns earlier than every flagged frame — nowhere near them. D3 mark-adoption is not implicated.

**Fix 1 — TimelineCanvas.tsx's second `useLayoutEffect`.** It used to write `container.scrollLeft` then immediately read it back (`setScrollLeft(container.scrollLeft)`) to capture the browser's own clamped value — a classic forced-reflow write-then-read, right after the same commit had just repositioned every mark for the new `pixelsPerYear`. Replaced with a clamp computed in plain JS (`Math.max(0, Math.min(target, totalWidth - viewportWidthPx))`) against values already known from state — no DOM read-back at all. The mount-path branch also stopped re-reading `container.clientWidth` (redundant: `effectiveViewportWidthPx` state already holds the same number from the earlier mount-measurement effect, and the container's own box size doesn't change when a lane's *content* width grows). The zoom/pinch-recenter branch still reads `container.clientWidth` once (matches existing, tested behavior; not on the initial-hydration path anyway). Verified: post-fix, this effect's code no longer appears among `ForcedReflow`'s flagged call frames at all.

**Fix 2 — Minimap's mount-then-unmount (found by @sergei, mid-investigation).** `viewport.ts`'s `useIsMobileViewport` deliberately returns `false` from `getServerSnapshot` always, matching the prerender's desktop-only assumption (ADR 0013) — so a real mobile visitor's *first* hydration commit still renders with `isMobileViewport = false`, same as the server, and only corrects a beat later via `useSyncExternalStore`'s post-commit check. Since Minimap's render guard is `!isMobileViewport`, this means Minimap actually **mounts** on that first commit for every mobile visitor too, then unmounts once the real value lands — visibly ("I can see it appear for a second in mobile emulation"). Minimap sits in the same flex column as `.scrollContainer` (`flex: 1 1 auto`), so that mount/unmount resizes the scroll container's own height, not just Minimap's own ~76px area — a second, independent, and probably larger contributor to the CLS/forced-reflow regression than the effect-ordering fix above. Fixed by adding `isMinimapIdle` (false at SSR and at the first hydration commit on every device, flips true via `requestIdleCallback`/`setTimeout` fallback — same pattern as `locale-datasets.ts`'s existing Tier 1 idle-prefetch) and gating Minimap on `!isMobileViewport && isMinimapIdle`. Minimap now never mounts at all for a real mobile visitor, and appears one idle tick later than before on desktop (an accepted trade for a secondary nav aid). Updated the 4 tests that assumed Minimap renders synchronously after `render()` to use RTL's `findByTestId`/await instead.

**Residual finding after fixes 1–2 — not fully closed.** Repeated trials (fresh isolated browser contexts, cold cache, identical post-fix bundle) were **not deterministic**: some runs showed CLS 0.00 and no `ForcedReflow` insight at all; others still showed CLS 0.51 with the *same* three remaining hotspots (PeopleLane's `scrollHeight` pin, TimelineCanvas's own mount-measurement `clientWidth` read, and the pan-listener mount).

**Fix 3 — collapse the two-hop `pixelsPerYear` correction into one (@sergei: "can we unify pixelsPerYear for desktop and mobile?").** Root cause of the intermittency: `viewport.ts`'s `isMobileViewport` state is deliberately still `false` on a real mobile visitor's first commit (same SSR-matching reason as Fix 2). TimelineCanvas's mount-measurement effect closed over that stale value, so a real mobile visitor's `pixelsPerYear` went through **two** corrections, not one — fallback-desktop-guess → real-width-still-desktop-years (an intermediate, never-intended state) → real-width-mobile-years — each one repositioning every mark. `MOBILE_DEFAULT_VISIBLE_YEARS` itself is a deliberate, spec'd UX decision (`.scratch/mobile-responsive-layout/spec.md` — mobile should genuinely show fewer years, not the same range smaller/denser) and stays; what's fixed is *when* the mount effect learns the real breakpoint. Added `viewport.ts`'s `isMobileViewportNow()` (a plain, non-hydration-safe `matchMedia` read — safe here because this effect runs strictly after the first commit, not during hydration reconciliation) and used it instead of the closed-over `isMobileViewport` prop for the `visibleYears` decision, while keeping `isMobileViewport` as the effect's dependency (so a genuine runtime breakpoint crossing still re-measures — that re-run just recomputes the same already-correct value the first time, a no-op React bails out of). Verified: the pan-listener hotspot disappeared entirely post-fix, and total `ForcedReflow` time dropped further (~566ms vs ~750-810ms) in the trials that still showed a shift.

**CLS itself did not reach a consistent 0.00.** Re-ran 3 more fresh-context trials after Fix 3: all 3 still showed CLS 0.51, `CLSCulprits` still "No potential root causes identified." This is expected, not a fix failure: the marks are already visibly painted at build-time-assumed positions the instant the browser receives the prerendered HTML (that's the point of ADR 0013's prerendering — real content before any JS runs), at `REFERENCE_PIXELS_PER_YEAR` (computed from `FALLBACK_VIEWPORT_WIDTH_PX = 1000`, desktop-shaped). Any visitor whose *real* viewport width differs enough from that fixed assumption will see marks visibly move once hydration corrects `pixelsPerYear` to the real value — no matter how cheaply or synchronously that correction is computed, because the "before" state was already on-screen, not just computed-but-unpainted. Mobile (390px vs. an assumed 1000px, correctly zoomed to 50 years vs. previously-also-briefly-120) diverges enormously from the assumption, so it shows a large, real shift every time; a desktop visitor near 1000px wide would see little or none. **This part is genuinely architectural** (a single fixed prerendered viewport assumption, ADR 0013) and isn't something a `TimelineCanvas.tsx`/`viewport.ts` effect-ordering fix can close — would need viewport-aware prerendering (e.g. a second mobile-shaped prerendered variant) to fully eliminate. Not attempted here.

**Net effect of fixes 1–3:** real, verified reductions in forced-reflow work and one whole intermittency source (the isMobileViewport-driven double correction) eliminated outright, LCP's render-delay improved materially in the trials that didn't hit the remaining architectural shift. CLS itself was unchanged in the worst case (0.51) because its root cause — prerendering always assuming desktop — wasn't in scope for this ticket's original read/write-ordering framing.

**Fix 4 — stop deriving `pixelsPerYear` from viewport width at all (@sergei: "does it need to shrink really? we can fix the left edge on screen and allow browser to calculate what gets in a viewport").** The architectural gap above assumed the fix had to be "prerender the right width" (infeasible on GitHub Pages' static hosting, no server-side device detection). The actual fix was the opposite move: stop needing to know the visitor's width for the initial zoom level at all. `pixelsPerYear` is now always `REFERENCE_PIXELS_PER_YEAR` (a fixed density) on mount, on every device — `MOBILE_DEFAULT_VISIBLE_YEARS` and the two-commit "wait for the real width, then correct" dance are gone entirely; a narrower viewport just shows fewer years at the same density instead of a rescaled range. Since prerendering always builds at this same fixed density (`REFERENCE_PIXELS_PER_YEAR = defaultPixelsPerYear(FALLBACK_VIEWPORT_WIDTH_PX)`), every mark's x-position is now identical between the prerendered HTML and whatever hydration computes, on every real device — hydration's correction pass literally cannot disagree with what's already painted, because there's no width-dependent computation left to disagree. Verified: CLS dropped from a deterministic 0.51 to a deterministic 0.29 across repeated fresh-context 2x-CPU trials, and `ForcedReflow`'s total time dropped further (~410ms, down from ~750-810ms).

**Residual 0.29, root-caused: two vertical/horizontal scroll-position corrections, not pixelsPerYear.** Fix 4 closed the *density* mismatch but not two separate, pre-existing *scroll-position* mismatches, both invisible to the original two-suspect framing because they don't touch `pixelsPerYear`:
- `.scrollContainer`'s mount effect centers on `DEFAULT_VIEWPORT_START_YEAR` (1740) via `scale(DEFAULT_VIEWPORT_START_YEAR) - clientWidth/2`-style centering, but `scale`'s domain starts at `PAN_MIN_YEAR` (-801) — the prerendered HTML's native scroll position is 0 (leftmost/-801), so hydration's correction is a ~21,000px horizontal jump on a 390px mobile viewport.
- `PeopleLane`'s pin-to-bottom (`el.scrollTop = el.scrollHeight`) was suspected in the residual-finding comment above but **empirically disproven** as a contributor on its own: disabling it client-side changed CLS not at all (0.2920 both ways, confirmed via a live `PerformanceObserver('layout-shift')` harness, not just the trace tool's own heuristic). The real defect there was upstream of the scroll-jump: `PeopleLane.tsx`'s `<svg>` has no `height` in its JSX at all (D3 fully owns that attribute post-mount, by design, to avoid fighting a filter-change transition) — so the *prerendered* svg has no real height, `.bottomAlign`'s `min-height: 100%` pads it to exactly fill `.peopleLane`, and `scrollHeight === clientHeight` (no overflow) right up until D3's mount effect sets the real height a beat later. `.scrollContainer`'s jump was the dominant, deterministic ~0.29 by itself; the vertical one was real but too small on its own to move the needle in these trials.

Root-caused via a `initScript`-injected `requestAnimationFrame` loop logging `.scrollContainer`'s `scrollLeft` and `.peopleLane`'s `scrollTop`/`scrollHeight` every frame from navigation start — showed both flat at their native defaults (0, and `scrollHeight === clientHeight`) for the first ~10 frames, then both jumping together the instant hydration's effects commit.

**Fix 5 — bake both corrections into the prerendered HTML itself, computed once, matching the client exactly.**
- `PeopleLane.tsx`: added `const [initialSvgHeightPx] = useState(() => totalHeight)`, same frozen-at-mount pattern already used for `initialPeopleHtmlProp`, and passed it as the `<svg>`'s real `height` prop. Frozen state never changes across re-renders, so D3's exclusive ownership of the attribute after mount is untouched — this only fixes what the very first paint (server or client) has before D3's mount effect has ever run.
- `vite-plugins/prerender-default-viewport.ts`: the SSR pass now also `ssrLoadModule`s `options.ts`/`shared/config/viewport.ts` to compute `scale(DEFAULT_VIEWPORT_START_YEAR)` via the real `buildXScale` (not a hand-copied formula, so it can't drift from the client's own value), and injects one inline `<script>` right after the prerendered markup that sets `.peopleLane`'s `scrollTop` and `.scrollContainer`'s `scrollLeft` to those exact values before the browser's first paint — the same FOUC-prevention timing trick as an early dark-mode class toggle (a parser-blocking script placed after the content it measures, so the browser has already laid it out by the time the script runs; confirmed via the same rAF-logging harness that both values now land within the first couple of frames, well before hydration). `.scrollContainer`'s clamp against `scrollWidth - clientWidth` still runs in that inline script against the real DOM, since only the real browser knows a given visitor's `clientWidth`.

Verified: 3 fresh isolated-context trials at 2x CPU throttle all show **CLS 0.00**, deterministically (down from 0.29, and 0.51 before Fix 4). `ForcedReflow` still flags ~270ms of unavoidable layout-measurement cost (reading `scrollHeight`/`clientWidth` once each, both in the inline script and again — as a no-op — in React's own mount effects), but with no attributable layout shift left for `CLSCulprits` to (still) fail to name. Full test suite (322 tests), typecheck, lint, and lint:boundaries all pass.
