# 05 — Preload every font weight the prerendered default viewport actually uses

**What to build:** A fix, not new behavior — `vite-plugins/critical-font-preload.ts`'s allowlist predates [[03-build-time-prerender-of-the-default-viewport]] and was scoped for a world where nothing painted before JS ran (its own comment: "the English UI chrome text"). Now that real content paints immediately, that allowlist misses fonts the prerendered default viewport genuinely needs: `Sidebar.module.css`'s `.headerTitle` (Fraunces 600) and `.heading` (Archivo 600) are part of first paint, and real People-lane entries within the default viewport (e.g. "Frédéric Chopin", "René Descartes", "Alī ibn Abī Ṭālib") need `archivo-latin-ext-400` for their accented characters — none of which are preloaded today. Because these fonts are only discoverable via `main.css`'s deferred `@font-face` rules, they load late under throttling and their arrival swaps text metrics, reflowing an already-painted mark and registering it as a new, larger LCP candidate. Found while verifying [[04-verify-and-record-the-lcp-win]] — see that ticket's `## Comments` for the full trace evidence (CLS 0.51, final LCP ~11s on both locales under Slow 4G + 4x CPU, vs. ~1.4s at true first paint).

**Blocked by:** 04.

**Status:** done (font-preload fix landed and verified; the CLS/late-LCP regression itself turned out to have a different cause — see Comments)

- [x] `critical-font-preload.ts`'s `CRITICAL_FONT_PATTERN` (or an equivalent explicit list) also preloads: `archivo-latin-ext-400` (accented People-lane names within the default viewport), `archivo-latin-600` and `fraunces-latin-600` (Sidebar `.heading`/`.headerTitle`, part of first paint on both mobile and desktop layouts).
- [x] Still no Cyrillic/Vietnamese subsets, and no weights genuinely absent from first paint — don't broaden past what's actually load-bearing, per the plugin's existing comment's own reasoning.
- [x] `critical-font-preload.test.ts` updated to assert the new set of preloaded hrefs.
- [x] Re-run the same trace from issue 04 (`dist/` build, `vite preview`, mobile viewport, Slow 4G + 4x CPU, both locales) — see Comments: the fonts now load early (all 5 finish by ~1.3s) and are no longer implicated by `CLSCulprits`, but CLS and the late LCP candidate are **unchanged** (still ~0.51 / ~11s). The regression's actual cause is not font loading — corrected below.

## Comments

**The font-preload fix itself is correct and shipped**: `CRITICAL_FONT_PATTERN` now preloads `archivo-latin-{400,600,700}`, `archivo-latin-ext-400`, and `fraunces-latin-600` (was `archivo-latin-{400,700}` only). Re-verified against a fresh `dist/` build: all 5 preloaded fonts finish loading by ~1.3s (previously `fraunces-latin-600`/`archivo-latin-600`/`archivo-latin-ext-400` only loaded once the deferred `main.css` was reachable, well after first paint). Re-running the same Slow-4G + 4x-CPU trace from issue 04, `CLSCulprits` no longer implicates any font — "No potential root causes identified" for the shift, confirming the fonts are no longer the trigger.

**But the regression from issue 04 is unchanged**: CLS is still ~0.51 and the final LCP candidate ("United States Declaration of Independence") still lands at ~11.2s on EN (11,217 ms this run vs. 10,852 ms pre-fix — same ballpark, not improved). **Issue 04's hypothesis was wrong** — fonts were a correlated-but-innocent bystander (they happened to finish loading around the same wall-clock time as the real cause, under the same throttle, which is why `CLSCulprits` pointed at them originally), not the actual trigger.

**Corrected root cause**: `performance.getEntriesByType('resource')` shows a ~9.3s dead zone with zero network activity between the initial bundle/data loads finishing (~1.9s) and the `*.tier1.js` fetches starting (~11.2s) — the main thread is fully occupied that whole time. `LCPBreakdown` agrees: render delay is 99.9% of the reported LCP, not resource load. The `ForcedReflow` insight additionally found ~1.8s of forced-synchronous-layout time inside `main-*.js`, consistent with `TimelineCanvas.tsx`'s initial-viewport-centering logic (`container.clientWidth`/`getBoundingClientRect` reads around scroll setup) and/or the D3 mark-adoption path ([[02-d3-join-adoption-logic]]) doing per-node layout reads across ~244 marks. Under 4x CPU throttle this is enough to stretch hydration + first client-side layout pass past the 11s mark, at which point the milestone label's SVG text box settles into its final size/position and — per the LCP spec's "last candidate before input" rule — retroactively becomes the reported LCP element, even though it was already visually present and stable-looking since ~1.4s.

**Is this worth chasing further?** Genuinely unclear, and not attempted here — `pre-launch-readiness` issue 14 hit the same shape of finding pre-ADR-0012 ("render delay dominated by fetch+parse under constrained bandwidth/CPU, not any single fixable bug") and stress-throttle profiles like Slow-4G+4x-CPU are deliberately harsh (harsher than Lighthouse's own default mobile throttle — see issue 17's note). The first-paint number this whole prerender effort targeted (~1.4s, ADR 0013) is real and unaffected by any of this. Left as an open question rather than a new speculative ticket — the CLS/late-candidate finding is now correctly attributed but not fixed.
