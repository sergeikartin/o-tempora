Type: research
Status: resolved

## Question

What's actually causing the Wikidata Query Service failures documented in `CLAUDE-activeContext.md` (widespread 502s/timeouts across most era buckets during the most recent Fetch re-run, plus an uncaught crash in `fetch-events.ts`'s `fetchEvents` on the first-page case)? What do Wikidata's own docs say about WDQS limits/best practices, and what concrete, low-risk redesign options follow for whatever stays on live SPARQL (Wars outside 1600-1973, Events & Inventions unless Vetustas fully replaces it)?

## Summary

Two independent problems, not one:

1. **The crash** is a straightforward missing-try/catch bug, fully explained by reading the code — `fetchEvents()` has no guard around either of its two `fetchAllPages` calls, unlike `fetchPeople()` and `fetchReigns()` which both wrap their fetch calls in per-bucket/per-batch `try/catch`.
2. **The 502s/timeouts** are ambient Wikidata Query Service instability that WMF's own operational docs describe as a known, recurring failure mode (Blazegraph deadlocks, elevated 5xx ratios) rather than something specific to this codebase's queries — but this codebase's retry logic only retries HTTP 429, never 502/503/504, which is exactly the error class WMF's own incident-response guidance says to retry with exponential backoff. That gap, not query complexity per se, is the highest-leverage fix.

## Current implementation

### The paginated client — `packages/data-pipeline/fetch/wikidata-client.ts`

- `ENDPOINT = "https://query.wikidata.org/sparql"` (`wikidata-client.ts:4`)
- `USER_AGENT = "same-sky-data-pipeline/0.1 (personal project; contact sergei.kartin@gmail.com)"` (`wikidata-client.ts:6-9`) — already sent on every request via the `User-Agent` header (`wikidata-client.ts:26`)
- `MAX_RETRIES = 3`, `PAGE_DELAY_MS = 500` (`wikidata-client.ts:11-12`)
- `REQUEST_TIMEOUT_MS = 30_000` — a 30-second client-side `AbortSignal.timeout` on every request (`wikidata-client.ts:18,29`)
- `runSparqlQuery()` (`wikidata-client.ts:20-48`): retries **only on HTTP 429** (`wikidata-client.ts:32-39`), honoring the `Retry-After` header when present, falling back to `5 * attempt` seconds. Any other non-OK response (**including 502/503/504**) throws immediately on the first attempt — no retry, no backoff (`wikidata-client.ts:41-44`).
- `fetchAllPages()` (`wikidata-client.ts:61-96`): pages via `LIMIT`/`OFFSET`, doc comment explains the LIMIT/OFFSET choice and notes "OFFSET cost on the query service grows with depth" (`wikidata-client.ts:55-56`, code-internal claim, not independently verified against a WMF source in this research pass). If a page fails **after** at least one page has already succeeded, it logs a warning and stops, keeping partial results (`wikidata-client.ts:75-81`). If the **first page** fails, the error is rethrown (`wikidata-client.ts:82`) — this is the mechanism the crash depends on.

### The crash — `packages/data-pipeline/fetch/fetch-events.ts`

`fetchEvents()` (`fetch-events.ts:17-31`) calls `fetchAllPages(buildHistoricalEventsQuery, ...)` (`fetch-events.ts:21`) and then `fetchAllPages(buildInventionsQuery, ...)` (`fetch-events.ts:27`) with **no try/catch around either call**. If either query's first page fails (502, timeout, or anything else), `fetchAllPages` rethrows per the mechanism above, and that exception propagates straight out of `fetchEvents()` uncaught, killing the whole Fetch run before the later stages (or, for the inventions query specifically, before its own raw file is ever written) can run. This exactly matches `CLAUDE-activeContext.md`'s "crashed uncaught while fetching inventions candidates."

Contrast with the two other fetchers, which both already guard against this:
- `fetchPeople()` (`fetch-people.ts:64-95`) wraps each era bucket's `fetchAllPages` call in its own `try/catch`, logging and continuing to the next bucket on failure (`fetch-people.ts:72-86`).
- `fetchReigns()` (`fetch-reigns.ts:40-72`) wraps each ID-batch's `runSparqlQuery` call in its own `try/catch`, logging and continuing to the next batch on failure (`fetch-reigns.ts:55-64`).

`fetchEvents()` is the one fetcher that never adopted this pattern.

### Era-bucketing — `packages/data-pipeline/fetch/fetch-people.ts`

- `PAGE_SIZE = 500` (`fetch-people.ts:8`), `MAX_PAGES_PER_BUCKET = 20` (`fetch-people.ts:18`, comment notes this was lowered from a pre-bucketing 40/one-scan value, and that live spot-checks found offset depth up to ~20,000 "stays inside the query service's empirically reliable range")
- 26 birth-year buckets (`fetch-people.ts:33-60`), narrowing from millennium-wide in antiquity to decade-or-finer from 1700 onward, specifically to work around the query service returning matches in an order that tracks ascending Wikidata QID with no `ORDER BY` (sorting by sitelinks was found to time out) — so an unbucketed scan exhausted its whole page budget inside antiquity before ever reaching modern rows.
- Each bucket is `try/catch`-guarded (`fetch-people.ts:72-86`); **no delay is inserted between buckets** — the loop moves directly from one bucket's `fetchAllPages` call to the next with no `sleep()`, unlike the 500ms `PAGE_DELAY_MS` used *between pages within* a bucket (`wikidata-client.ts:92`) and the 500ms `BATCH_DELAY_MS` used *between batches* in `fetchReigns()` (`fetch-reigns.ts:15,65`).

**By contrast, the two events queries (`buildHistoricalEventsQuery`, `buildInventionsQuery`, called from `fetch-events.ts`) have no era-bucketing at all** — flat `PAGE_SIZE = 500`, `MAX_PAGES = 10` (`fetch-events.ts:8-9`, offset only ever reaches 4,500), no year-range parameter on either query builder (`queries/historical-events.ts:28`, `queries/inventions.ts:7`).

### Query shapes — `packages/data-pipeline/fetch/queries/`

- `MIN_SITELINKS = 30` (`queries/min-sitelinks.ts:4`), shared by all three query builders as a `FILTER` threshold — a fixed numeric range filter, applied consistently.
- `buildPeopleQuery` (`queries/people.ts:32-56`): one required triple pattern block (`wdt:P31 wd:Q5`, `wdt:P569`, `wikibase:sitelinks`) plus **6 `OPTIONAL` blocks** (label, deathDate, occupation, country, Wikipedia article via `schema:about`/`schema:isPartOf`, description) (`queries/people.ts:47-52`).
- `buildHistoricalEventsQuery` (`queries/historical-events.ts:28-54`): an 8-value `VALUES ?type {...}` list (`queries/historical-events.ts:17-26`, deliberately a flat class list rather than a `wdt:P279*` transitive walk, per the inline comment noting the transitive form "reliably times out against the live query service at this corpus size") plus **7 `OPTIONAL` blocks** (`queries/historical-events.ts:35,36,39-49`), one of which (`?event wdt:P361 ?partOf`) itself nests a second `OPTIONAL` for the parent's label.
- `buildInventionsQuery` (`queries/inventions.ts:7-20`): the simplest of the three — one required pattern (`wdt:P575`, `wikibase:sitelinks`) plus **4 `OPTIONAL` blocks**.
- `buildReignsQuery` (`queries/reigns.ts:16-26`): parameterized on a `VALUES ?person {...}` list of already-known Q-IDs (batched at 50 per call, `fetch-reigns.ts:14`) rather than a corpus scan — structurally the cheapest and most targeted of the four query shapes, and the only one using the full `p:`/`ps:`/`pq:` statement model (needed for qualifiers, per the inline comment).

None of the four query builders use `SERVICE wikibase:label` (all use the cheaper direct `rdfs:label`/`FILTER(LANG(...))` pattern) or `ORDER BY` — both already align with WMF's own optimization guidance (see below).

## Wikidata Query Service documented limits and best practices

Sources: Wikidata Query Service User Manual, the community SPARQL query-optimization page, the WDQS operational runbook, the WDQS incident/status-report page, and the Wikimedia Foundation User-Agent policy.

- **Hard query deadline: 60 seconds.** "There is a hard query deadline configured which is set to 60 seconds," applying to both the web UI and the public SPARQL endpoint. — [Wikidata Query Service/User Manual](https://www.mediawiki.org/wiki/Wikidata_Query_Service/User_Manual)
  - This codebase's own client-side `AbortSignal.timeout(REQUEST_TIMEOUT_MS)` is set to **30 seconds** (`wikidata-client.ts:18,29`) — half of Wikidata's own server-side budget. A query that Wikidata would still be actively (and successfully) working on at 31-59 seconds is currently aborted client-side and logged/treated as a failure before the server ever gets a chance to finish it.
- **Per-client throttling**: "One client (user agent + IP) is allowed 60 seconds of processing time each 60 seconds," "One client is allowed 30 error queries per minute," and currently "5 parallel queries per IP." Exceeding these returns HTTP 429 with a `Retry-After` header; repeated 429 violations (not backing off) leads to bans. — [Wikidata Query Service/User Manual](https://www.mediawiki.org/wiki/Wikidata_Query_Service/User_Manual)
  - The pipeline already runs fully serially (one request in flight at a time) and already honors `Retry-After` on 429 (`wikidata-client.ts:32-39`), so it's already compliant here; this isn't the observed failure mode (the team saw 502s/timeouts, not 429s).
- **User-Agent policy**: automated requests must send a descriptive `User-Agent` — `<client name>/<version> (<contact info>) <library/framework>` — non-compliant requests risk an HTTP 403 with "Scripts should use an informative User-Agent string with contact information, or they may be blocked without notice." — [Wikimedia Foundation User-Agent policy](https://foundation.wikimedia.org/wiki/Special:MyLanguage/Policy:User-Agent_policy)
  - Already satisfied: `USER_AGENT` includes name, version, and a contact email (`wikidata-client.ts:6-9`). One gap against the documented best practice: WMF's guidance recommends including the string "bot" in the agent to aid traffic classification, which this string does not do. Low-risk, optional tweak.
- **502/504 root cause is server-side, not client-query-specific**: the WDQS runbook describes Blazegraph occasionally deadlocking ("the cause of deadlocked queries is unknown; it seems to be more likely with queries of higher complexity, but there is no single type of query that can cause the issue"), and a `BlazegraphFailedServerRatioIncrease` alert firing on sustained 5xx-ratio increases — i.e., this is a known, recurring, cluster-wide instability mode, not something guaranteed fixable purely by rewriting one query. — [Wikidata Query Service/Runbook](https://wikitech.wikimedia.org/wiki/Wikidata_Query_Service/Runbook)
  - This matches the project's own observation in `context/progress-tracker.md` (this worktree): a live re-test of the *exact same* query that had just failed with a 502 succeeded moments later — consistent with WMF's own characterization of this as ambient instability rather than a structural query bug.
  - Corroborated by current incident reports: a May 2026 report of query delays exceeding 60 seconds and occasional 502s (tracked as Phabricator T425861), and elevated "maxlag" through mid-to-late July 2026 affecting bot-class API traffic. — [Wikidata:Report a technical problem/WDQS and Search](https://www.wikidata.org/wiki/Wikidata:Report_a_technical_problem/WDQS_and_Search)
- **Official guidance for handling instability**: for incomplete/error responses (including from timeouts), WMF staff guidance on the technical-problems page is to "implement retry logic with exponential backoff." The same page also recommends checking the [WDQS Grafana dashboard](https://grafana.wikimedia.org/d/000000489/wikidata-query-service?viewPanel=8&orgId=1) for current lag before submitting large queries. No official guidance was found recommending a specific off-peak time window. — [Wikidata:Report a technical problem/WDQS and Search](https://www.wikidata.org/wiki/Wikidata:Report_a_technical_problem/WDQS_and_Search)
  - This directly targets the gap identified above: this codebase currently has **zero retry/backoff for 502/503/504**, the exact error class this guidance is about. Only 429 gets retried.
- **Query-optimization guidance** (community-maintained, not a hard limit but consistently repeated advice): fixed-value predicates (e.g., `wdt:P31 wd:Q5`) are "the cheapest option"; avoid `wdt:P279*`-style unbounded transitive property-path walks; avoid `SERVICE wikibase:label` in favor of direct `rdfs:label`/`FILTER(LANG(...))` for large result sets; "consolidate chained OPTIONAL patterns into single blocks when possible"; place `LIMIT` in inner subqueries before applying any label enrichment; a documented escape hatch, `hint:Query hint:optimizer "None"`, disables Blazegraph's own (sometimes wrong) query-plan reordering when a hand-ordered query is faster than what the optimizer produces. — [Wikidata:SPARQL query service/query optimization](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service/query_optimization)
  - This codebase's queries already follow the two biggest wins (fixed-value predicates for `wdt:P31`/type filters, no `SERVICE wikibase:label`, no `ORDER BY`, no unbounded `*` transitive walks — the historical-events query explicitly avoids the transitive form per its own inline comment). The one guidance item not yet applied is "consolidate/reduce OPTIONAL clauses" — the people and historical-events queries carry 6 and 7 `OPTIONAL` blocks respectively.
  - No specific numeric limit on `VALUES` clause size or `OPTIONAL` clause count was found in any of the fetched official/community pages — this project's own `BATCH_SIZE = 50` for `VALUES ?person` (`fetch-reigns.ts:14`) is a self-imposed conservative choice (per its own inline comment), not derived from a documented Wikidata ceiling.
  - No official documentation was found stating a specific numeric OFFSET/pagination-depth ceiling either — this codebase's own inline comments (`wikidata-client.ts:55-56`, `fetch-people.ts:11-18`) describe an *empirically* observed "soft ceiling" (~20,000 offset reliable, 25,000+ unreliable) from the team's own live spot-checks, not from a Wikidata source. Treat that number as project-local, not officially guaranteed.

## Concrete, low-risk redesign options

Ordered roughly by expected impact-to-risk ratio, all scoped to what stays on live SPARQL (Wars outside 1600-1973, Events & Inventions).

1. **Retry 502/503/504 with exponential backoff in `runSparqlQuery`, not just 429.** Currently the single largest gap between this code and WMF's own stated guidance ("implement retry logic with exponential backoff") for exactly the error class the team is hitting. Mechanically small: widen the retry condition at `wikidata-client.ts:32` from `response.status === 429` to also cover 502/503/504, and replace the 429-specific `Retry-After`-driven delay with a simple exponential backoff (e.g. `2^attempt` seconds, capped) for the new cases, since 502/504 responses don't carry a `Retry-After` header.
2. **Add a try/catch around each `fetchAllPages` call in `fetch-events.ts`'s `fetchEvents()`**, mirroring the existing per-bucket pattern in `fetch-people.ts:72-86` and per-batch pattern in `fetch-reigns.ts:55-64`. This directly fixes the documented crash and is a minimal, isolated change (no query or pagination logic touched).
3. **Reconcile the 30-second client-side `REQUEST_TIMEOUT_MS` with Wikidata's own 60-second server-side hard deadline.** Raising it toward (e.g.) 55 seconds gives legitimately slow-but-otherwise-healthy queries the same budget the server itself allows, rather than self-aborting before the server would have. This doesn't address true 502s (those are the server failing outright, not merely being slow) but removes a self-inflicted source of "failure" for queries the server would have completed.
4. **Era-bucket the two events queries the same way `fetch-people.ts` already buckets people.** Add a `[minYear, maxYearExclusive)` parameter and date `FILTER` to `buildHistoricalEventsQuery`/`buildInventionsQuery` (structurally identical to `buildPeopleQuery`'s existing `formatYearAsSparqlDateTime`/`FILTER(?birthDate >= ... && ?birthDate < ...)` pattern at `queries/people.ts:26-30,46`), and loop `fetch-events.ts` over buckets the way `fetch-people.ts:70-87` already does. This both narrows per-request result/join size (the community optimization guidance's general direction) and, combined with fix #2, means one bucket's failure no longer threatens the whole run — consistent with the exact bug class ("wide, unbounded scan starves later/other data") that the people-lane fix (`context/progress-tracker.md`, "Data-pipeline bug fix" entry) already solved once for people.
5. **Add a courtesy delay between era buckets in `fetch-people.ts`**, matching the existing `PAGE_DELAY_MS`/`BATCH_DELAY_MS` pattern already used between pages and between reign-fetch batches — currently the only gap in the codebase between an otherwise-consistent "pause between successive Wikidata requests" convention. Cheap, mechanical, low-risk.
6. **Reduce `OPTIONAL` clause count in the people and historical-events queries**, per the community guidance to consolidate chained `OPTIONAL`s. Concretely, the events query's nested `partOfLabel` `OPTIONAL` (`queries/historical-events.ts:47-50`) is the deepest/most expensive-looking one; splitting the "core fields" query from a smaller "enrichment" follow-up (label/description/article only, for whatever candidate IDs the core query already returned) would mirror the project's own existing precedent of one Fetch query depending on another's raw output (`fetchReigns()` already does this for people IDs, documented in `CLAUDE-decisions.md`'s "Architecture Decisions Log"). Higher effort than 1-5; worth doing only if 1-5 don't sufficiently improve reliability on their own.
7. **Optional: append "bot" to the `User-Agent` string** (`wikidata-client.ts:6-9`) to align with WMF's stated best practice for traffic classification. Cosmetic; not expected to change reliability, since the current string is already compliant with the hard 403-triggering requirement (name, version, contact).
8. **Not recommended given available evidence: off-peak scheduling.** No official Wikidata documentation found recommending or describing a specific low-traffic window for the public WDQS endpoint; the only concrete pre-flight guidance found is checking the WDQS Grafana lag dashboard immediately before a large run, which could be added as an optional manual step but isn't automatable without new tooling and isn't a documented Wikidata recommendation to build around.
