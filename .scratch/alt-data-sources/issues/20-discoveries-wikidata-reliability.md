# 20 — Discoveries & Inventions: Wikidata reliability fixes

**What to build:** A live pipeline Fetch run for Discoveries & Inventions completes reliably against the Wikidata Query Service, without the crash or the failure modes documented in the most recent broken run.

**Blocked by:** 18 — Output: split into wars.json/discoveries.json (this ticket's output target is `discoveries.json`).

**Status:** done

- [x] `runSparqlQuery` retries HTTP 502/503/504 with exponential backoff (`2s * 2^(attempt-1)`, `MAX_RETRIES = 3`), in addition to the existing 429/`Retry-After` handling. Covered by new `wikidata-client.test.ts` (mocked `fetch` + `node:test`'s `mock.timers`, no real network/delay).
- [x] `fetchEvents()` in `fetch-events.ts` was rewritten so **both** of its query calls (historical-events and inventions) are wrapped in try/catch, matching the per-bucket pattern the pre-Pantheon people fetcher established — one bucket failing (or the whole historical-events half failing) can no longer crash the run or prevent the inventions/discoveries half from completing and being written.
- [x] Client-side `REQUEST_TIMEOUT_MS` raised from 30s to 55s, close to Wikidata's documented 60s hard deadline (research ticket 08's recommendation), leaving a small margin so the client's own timeout fires (and can be retried) before the server would kill the connection uncleanly.
- [x] Both `buildHistoricalEventsQuery` and `buildInventionsQuery` gained a `[minYear, maxYearExclusive)` parameter and matching `?date` filter (shared `formatYearAsSparqlDateTime` helper, extracted to `queries/format-sparql-date.ts`, mirroring the pre-Pantheon `buildPeopleQuery`'s pattern), and `fetch-events.ts` loops both over the same 26 era buckets the people fetcher used, each bucket independently try/catch-guarded.
- [x] Live re-run verified end to end against the real Wikidata Query Service (not mocked): all 26 buckets succeeded for both queries with zero retries needed, zero bucket failures — 1,208 historical-event rows and 6,107 invention rows written to `data/raw/`. Ran `build-data`: `wars.json` 771 kept / 0 dropped, `discoveries.json` 3,102 kept / 2,601 dropped (missing name/Wikipedia article — pre-existing Score/Tag drop reasons, unrelated to this ticket). Spot-checked `discoveries.json` for sane content (French Revolution-era and modern entries present, year range -4000..2023, no duplicate IDs).

**Scope note**: `fetchEvents()` fetches both lanes (historical-events/Wars and inventions/Discoveries) in one function, so the reliability fixes above necessarily cover both query calls, not just inventions — this ticket's title tracks the *Discoveries & Inventions* lane specifically because that's the half being published here. Only `discoveries.json` was copied to `packages/shared-types/src/data/` (not via the full `publish-data` script, matching ticket 19's precedent) — `wars.json` stays unpublished until ticket 25 does its own live-verify-and-publish pass, even though the underlying `wars.json` this run produced already looks correct (771 entries, no CDB90 residue, matches the ticket 24 Wikidata-only reversal).

**Found during verification, not fixed (out of scope)**: World War II and the Thirty Years' War are absent from `events-historical.raw.json` — confirmed pre-existing (also absent from the previously-committed raw snapshot, before any of this ticket's changes), caused by Wikidata typing them under more specific subclasses (e.g. "world war", Q103495) not included in `historical-events.ts`'s `EVENT_TYPES` list. A query-completeness gap, not a reliability regression; flagged in `docs/active-context.md` for a future ticket.

**Found during implementation, fixed in the same unit (not originally in scope, but silently broke this ticket's own new test)**: `package.json`'s `test` script glob patterns (`fetch/**/*.test.ts` etc.) were being pre-expanded by `/bin/sh` (dash, this system's default shell), which doesn't support recursive `**` globbing — it silently dropped every test file living directly in a stage directory rather than a subdirectory. This meant `fetch/csv.test.ts` and `fetch/pantheon-row-shape.test.ts` were *already* silently not running via `npm test`, and this ticket's new `fetch/wikidata-client.test.ts` would have had the same fate. Fixed by quoting the glob patterns in the script string so `sh` passes them through literally and Node's own (correctly recursive) glob resolution handles them — `npm test` now genuinely runs all 65 tests, not 50.
