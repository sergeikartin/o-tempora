# 17 — People: switch to Pantheon

**What to build:** Regenerating the People dataset pulls from Pantheon 2.0 instead of Wikidata — a downloaded, checked-in raw CSV snapshot maps into `Person` records with occupation-domain and UN-region tagging and HPI-based fame tiers, and the old Wikidata-based People fetch path is removed.

**Blocked by:** None — can start immediately.

**Status:** done

- [x] `fetch-pantheon.ts` downloads Pantheon's 2025 Person Dataset `.csv.bz2` (public, unauthenticated), decompresses it via a new `seek-bzip` dependency (flagged and confirmed before adding — Node has no built-in bzip2 support and no system `bzip2`/`bunzip2` binary was available in this environment), and writes the plain CSV as a raw snapshot checked into git (38.9MB, in line with the existing 24MB precedent).
- [x] `pantheon-row-shape.ts` types and validates the consumed columns at the Fetch boundary (header-shape check + required-field check), backed by a hand-rolled RFC4180 CSV parser (`csv.ts`) — verified against real quoting/escaping edge cases in the actual file (embedded commas, escaped double-quotes) before deciding against a naive split.
- [x] `OccupationDomain`/`UnRegion` added to shared-types; `Person.category`/`occupationTags`/`regionTags: Region[]` replaced by `occupationDomain: OccupationDomain` (singular — Pantheon's `occupation` is single-valued) and `regionTags: UnRegion[]`.
- [x] `un-region-categories.ts`: hardcoded `bplace_country`/`dplace_country` → `UnRegion` table (222 entries), built from a live call to Pantheon's `/country` endpoint. **Deviates from the ticket's literal wording**: joins on country *name*, not ISO country code — the person CSV has no country-code column at all, only a name string, so a code-based join was never actually possible. Verified all 241 distinct country values in the real person data against the API's names; found and handled the 4 real mismatches directly (`"Bahamas, The"`/`"The Bahamas"`, `"Czech Republic"`/`"Czechia"`, `"Federated States of Micronesia"`/`"Micronesia"`, `"Swaziland"`/`"Eswatini"`).
- [x] `Person.fameScore` populated directly from `hpi`; new `FAME_TIER_MIN_HPI` (90/85/75, independent of the sitelink-based constant, which is untouched for Wars/Discoveries).
- [x] Verified against real, live data — not just fixtures: downloaded the actual current dataset (matches earlier research's counts exactly: 108/423/3,840 at the three HPI floors, 101 occupation values), ran all 77 description-fetch batches live with zero failures, regenerated `people.json` (3,680 kept), and spot-checked Newton/Muhammad/Buddha by hand (correct domain, region, dates, fame score; Muhammad's reign periods even came through via the stale-but-`wdId`-keyed reigns cache).
- [x] Old Wikidata-based People fetch code deleted: `fetch-people.ts`, `queries/people.ts`(+test), `transform/tag-people.ts`, `transform/occupation-categories.ts`, `transform/list-unmapped-occupations.ts`, and the now-orphaned `data/raw/people.raw.json` (24MB). `list-unmapped-countries.ts` updated to drop the people-specific config (Wars/Discoveries-only now).
- [x] CC BY-SA 4.0 data-license notice added (`packages/shared-types/LICENSE-DATA.md`), citing Yu et al. 2016; also covers Wikidata's CC0 for Wars/Discoveries.
- [x] Fixture-based unit tests across every layer: `csv.test.ts` (parser edge cases), `pantheon-row-shape.test.ts` (normal/BCE/empty-field rows, header validation), `tag-pantheon-person.test.ts` (occupation mapping incl. unmapped, region dedup incl. the alias case), `score.test.ts` (HPI tier nesting), `write-datasets.test.ts` (`buildPeople` incl. reigns-by-wdId, implausible lifespan, missing domain/description). 44 tests, no network I/O in any of them.

**Real scope discovered during implementation, not in the original spec**: Pantheon has no `description` field at all (only `occupation`, no bio-style text) — a gap missed by every earlier ticket. Resolved by user direction: `wikipediaUrl` derives from Pantheon's `slug` (no fetch needed), and `description` comes from a **new** secondary batched-SPARQL fetch (`fetch-descriptions.ts`, mirrors `fetch-reigns.ts`'s exact pattern) keyed on the retained `wd_id`, scoped to only the HPI-floor survivors (~3,840 of 126,582) via a new `MIN_HPI` Fetch-stage constant (mirrors the existing `MIN_SITELINKS` pattern, kept out of Transform to preserve the Fetch→Transform layering). `fetch/index.ts` no longer calls `fetchReigns()` — its input (`people.raw.json`) no longer exists; left unwired rather than broken, with `fetch-reigns.ts` itself untouched pending ticket 19.
