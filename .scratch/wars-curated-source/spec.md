# Wars & Conflicts: switch to a curated source, add Container nesting

## Problem Statement

The Wars & Conflicts lane is sourced from a 9-query Wikidata SPARQL corpus scan (one per `ConflictCategory`), the same kind of low-signal, no-real-classification approach that made Events & Inventions' original source produce junk top entries ("Brazil", "Antarctica") before that lane switched to a hand-curated list. Wars & Conflicts hasn't hit that exact failure mode yet, but the underlying problem is the same: nobody is choosing which conflicts matter, Wikidata's `instance of` claims are.

Separately, umbrella conflicts — a multi-century, multi-phase campaign like the Crusades, containing individual wars (Third Crusade), which in turn contain point-in-time battles (Siege of Acre) — have no way to be represented today. A prior effort ([.scratch/wars-conflicts-taxonomy/map.md](.scratch/wars-conflicts-taxonomy/map.md)) removed the one mechanism that gestured at this (`partOfWarName`, a free-text string) because a flat string can't reliably resolve to a real entity, and explicitly deferred "properly modeling multi-phase parent conflicts" as its own future effort. This is that effort.

## Solution

Migrate Wars & Conflicts to a curated-identity-plus-Wikidata-enrichment shape, structurally close to the two-stage pipeline Events & Inventions already uses (per [ADR 0008](packages/data-pipeline/docs/adr/0008-discoveries-sourced-from-curated-list-not-wikidata-query.md)) but narrower in what the curator authors by hand: the curator picks *which* conflicts matter, their Wikidata QID, their `category`, and any parent/child nesting — everything else (`description`, `image`, start/end dates, fame, Wikipedia URL, region) is backfilled by a batched per-QID Wikidata SPARQL enrichment pass, the same VALUES-clause pattern `fetch-events-enrichment.ts` already uses, extended to also pull `schema:description` and the P585/P580/P582 date claims `fetch-historical-events.ts`'s query already knows how to ask for. Unlike Discoveries, description and dates are never curator-authored here — Wikidata is still the source of fact, just addressed by curated QID instead of a blind `instance of` scan.

Alongside that migration, introduce **Container** — a curated `War` with no parent — as the top level of an optional, depth-capped nesting relationship (`parentId`) that lets an umbrella conflict (Crusades) genuinely contain sub-wars (Third Crusade) and, eventually, point-in-time events (Siege of Acre) as real, independently-curated entities rather than a label.

The curated list itself is supplied directly by the user (name, Wikidata QID, category, optional parent) — no Britannica scraping, no source-merge/dedupe tooling, no reusable bootstrap process. A one-off script converts whatever hand-off format the user provides into the checked-in curated JSON file; it exists to do that one conversion, not to be rerun against future sources.

**`ConflictCategory` shrinks to six values**: `war`, `war-of-independence`, `revolution`, `rebellion`, `coup-d-etat`, `military-operation` — every category that can stand on its own as a top-level conflict. `battle`, `siege`, and `peace-treaty` are removed from the taxonomy entirely, not just deferred — mirroring how Discoveries dropped `"invention"` from the old shared `Category` enum during its own migration. They're inherently sub-events of a war, not standalone conflicts; if/when nested sub-event detail (a specific battle or treaty within a war) gets designed, that's a future effort free to introduce whatever mechanism fits, not constrained by keeping unused categories around now.

**Shape is decoupled from both category and curator input — decided purely by what Wikidata's enrichment pass resolves.** Today only `war`/`war-of-independence` can ever render as a range bar (`War`); everything else is forced to a point (`WarEvent`), per the Wikidata-type-based rule the taxonomy restructure introduced (`BAR_RENDERED_TYPE_QIDS`). That rule is retired entirely: at Output, an entity whose enrichment resolves both a start and an end date becomes a `War` (a real `Period`); an entity that resolves only a single date (a Wikidata point-in-time claim, or a start with no end) becomes a `WarEvent`. Category still tags *what kind* of conflict it is; it never determines *how it renders*, and the curator never states shape directly — it falls out of whatever Wikidata actually knows about that QID.

## User Stories

1. As the curator, I want to hand off a plain list of conflicts — name, Wikidata QID, category, and optional parent — and have it become the checked-in curated file, so that I'm not hand-writing JSON or re-deriving anything Wikidata already knows (dates, description, fame, image, region).
2. As the curator, I want each curated conflict's `description`, dates, image, and region sourced from Wikidata automatically, so that I only ever author identity/classification/hierarchy — the three things Wikidata can't decide for me.
3. As the curator, I want to designate any curated `War` row as a **Container** by giving a child row a `parentId` pointing at it, so that the Crusades can be modeled as a real entity containing the Third Crusade as a real entity, rather than a string.
4. As the curator, I want the nesting depth capped at 3 levels (Container → sub-war/event → event) and enforced (bad data is dropped, not silently published), so that a curation mistake (an event parented to another event, or a chain deeper than 3 levels) can't reach the shipped dataset.
5. As a developer maintaining the pipeline, I want `transformWars`/`buildWars` to follow the same overall shape as `transformDiscoveries`/`buildDiscoveries` (read curated+enriched rows, no `groupRows` step, Output-stage validation with `DropReport`), so that the two lanes stay recognizable to the next person reading the code, even though what each curates differs.
6. As a developer, I want the old 9-query per-category SPARQL fetch, its per-category sitelink floors, and the cross-category dedup (`dedupeFirstById`) removed once the curated source lands, so that dead code allowing for a since-abandoned approach doesn't linger (mirrors Discoveries' own ticket 09, "remove old wikidata fetch").
7. As a developer, I want a boundary-validation function for the curated and enriched wars files (mirroring `validateCuratedEventsFile`/`validateEnrichedEventsFile`), so that a malformed hand-edited curated file fails fast with a clear error instead of corrupting the pipeline downstream.
8. As a developer, I want `parentId` validated at Output (the last stop before the frontend ever sees this data), so that a Container/depth-shape violation is caught and logged with a `DropReport` reason, the same posture Discoveries already takes on enrichment failure.
9. As a developer, I want a curated row's shape (range bar vs point) to follow whatever dates Wikidata's enrichment pass actually resolves — two dates becomes a `War`, one becomes a `WarEvent`, none gets dropped — rather than staying locked to today's fixed "only war/war-of-independence bar-render" rule.
10. As a product owner, I want this migration to touch data-pipeline and shared-types only — no rendering/UI changes for the nesting hierarchy in this pass — so that the visual design of nested conflicts (indentation, collapse/expand, grouped bars) gets its own dedicated design pass instead of being improvised here.
11. As a developer, I want `battle`, `siege`, and `peace-treaty` removed from `ConflictCategory` entirely (not left as unused, uncurated values), so that the taxonomy only contains categories this pass actually produces — `war`, `war-of-independence`, `revolution`, `rebellion`, `coup-d-etat`, `military-operation`; any `WarEvent`s that do appear in this pass come naturally from single-date entries among those six, proving `parentId` works end-to-end without needing artificial examples.
12. As the maintainer of the Wars & Conflicts color palette (`CONFLICT_CATEGORY_COLORS`) and its docs (`design-tokens.md`, `CONTEXT.md`), I want the three removed categories' entries dropped from all of them in the same unit of work, so that the codebase doesn't carry color/doc entries for categories that no longer exist.
13. As the maintainer of `docs/product-scope.md`, I want its stale claims corrected — "linked to their parent war when known" (the removed mechanism) and "Wars & Conflicts... from Wikidata" (no longer fully true once curated) — so that the scope doc doesn't contradict the shipped architecture.
14. As a developer, I want the `Container` term recorded as project vocabulary (domain doc/ADR), so that future contributors don't reinvent or misname the concept.

## Implementation Decisions

- **Curated ground-truth file** (`data/raw/wars-curated.raw.json`): per entry — `id` (bare Wikidata QID), `name`, `category` (the six-value `ConflictCategory`), and an optional `parentId` (another curated row's `id`). No `year`/`endYear`/`description`/`source` fields — unlike Discoveries, none of those are curator-authored here; they're either Wikidata-sourced (date, description) or dropped as unneeded (provenance, since there's exactly one source: the user's hand-off list).
- **Enrichment pass** (`fetchWarsEnrichment`, mirrors `fetch-events-enrichment.ts`): batched per-QID SPARQL (same `VALUES ?event { wd:Q… wd:Q… }` pattern), extended beyond Discoveries' field set with the date/description `OPTIONAL` blocks `fetch-historical-events.ts`'s query already has — `schema:description`, P585 point-in-time OR P580 start-time (with `wikibase:timePrecision`), and P582 end-time (with precision) — alongside `wikibase:sitelinks`→`fameScore`, an English Wikipedia `article`→`wikipediaUrl`, `wdt:P17` `country`→`regionTags`, and `wdt:P18`→`image`. Same enrichment-failure handling as Discoveries (row dropped at Output if the QID doesn't resolve a required field).
- **Container/nesting model**: no new type or discriminant field. A `War` with no `parentId` is a Container (level 1). A `War` or `WarEvent` with `parentId` pointing at a Container is level 2. A `WarEvent` with `parentId` pointing at a level-2 `War` is level 3 — the deepest level. Ranges (`War`) never appear below level 2; `WarEvent`s never parent other `WarEvent`s. `parentId` lives on both `War` and `WarEvent` in `packages/shared-types`, always resolving to another `War`'s `id`, never a `WarEvent`'s.
- **Output-stage validation**: `buildWars` (in `write-datasets.ts`) validates every `parentId` reference — resolves to a real row, resolves to a `War` (not a `WarEvent`), and doesn't exceed 3 levels of depth. A violation drops the offending row with a new `DropReport` reason, same "log it, don't publish it" posture as Discoveries' `missing sitelinks (enrichment failed)`.
- **`War`/`WarEvent` shape is enrichment-driven, not category- or curator-driven**: `buildWars` builds a `War` (with `period`) when the enriched row resolved both a start and an end date, and a `WarEvent` (with `at`) when it resolved only one — regardless of `category`. A row that resolves *no* date at all is dropped with a `missing date (enrichment failed)` `DropReport` reason, the same posture as Discoveries' missing-sitelinks drop. This retires `BAR_RENDERED_TYPE_QIDS`-style gating entirely. A Container is simply a `War` (any in-scope category, resolved both dates, no `parentId`) — not restricted to `category: "war"`.
- **`transformWars` rewrite**: reads the curated+enriched file directly (no `groupRows` step — already one row per conflict, same reasoning `transformDiscoveries`/`transformPeople` already document), replacing the 9-file SPARQL read + `dedupeFirstById` concatenation entirely.
- **Removed**: the 9 per-`ConflictCategory` SPARQL queries and their raw files, `CONFLICT_CATEGORY_QUERIES`' fetch-time role, `BAR_RENDERED_TYPE_QIDS`, the per-category sitelink floor logic in `score.ts` for Wars (curated data needs no floor, same as Discoveries), and `dedupeFirstById`'s Wars call site.
- **Bootstrap step**: a one-off script that reads whatever flat format the user hands off (name/QID/category/optional-parent) and writes `data/raw/wars-curated.raw.json` in the curated shape above. Not source-parameterized, not designed for repeated future re-bootstrap runs — if the list needs regenerating later, that's a new, separate script written for whatever that need actually looks like then.
- **`docs/product-scope.md` update**: correct the "linked to their parent war when known" and "from Wikidata" claims once this lands.
- **Domain vocabulary**: record "Container" (a top-level, parent-less `War` that other rows can nest under) in the project's domain doc/ADR.
- **`ConflictCategory` shrinks**: `battle`, `siege`, `peace-treaty` removed from `CONFLICT_CATEGORIES`/`ConflictCategory` in `packages/shared-types`, same as Discoveries dropped `"invention"`. Their `CONFLICT_CATEGORY_COLORS` entries (`packages/web/src/widgets/timeline-canvas/options.ts`) and `design-tokens.md`/`CONTEXT.md` references drop in the same unit of work. `tsc` forces every color-map/switch site to be updated (missing/extra keys), so this is largely a compiler-verified mechanical change.

## Testing Decisions

- Good tests here exercise the same seam Discoveries' own tests already use: `buildWars`/`transformWars` given synthetic rows, asserting on the resulting `War`/`WarEvent` shape and `DropReport` — not implementation details of how the SPARQL query is built or how the file is parsed.
- `write-datasets.test.ts`: extend with cases for `buildWars`'s new `parentId` validation — valid 2-level and 3-level chains kept; an event-parented-to-event, a parent reference to a nonexistent id, a parent reference to a `WarEvent`, and a chain exceeding 3 levels each dropped with the correct `DropReport` reason. Also cover the enrichment-driven shape logic directly: a row with both a start and end date builds a `War`, a row with only one date builds a `WarEvent`, a row with no date is dropped with `missing date (enrichment failed)` — independent of which of the six in-scope categories it carries.
- `transform/index.test.ts`: extend with a `transformWars` case reading a small synthetic curated+enriched fixture, mirroring the existing `transformDiscoveries` test.
- A new boundary-validation module (`validateCuratedWarsFile`/`validateEnrichedWarsFile`, mirroring `validateCuratedEventsFile`/`validateEnrichedEventsFile`) gets the same kind of shape tests — confirm by checking for an existing test file before writing a new one from scratch.
- The wars-enrichment query builder (`buildWarsEnrichmentQuery`, extending `buildEventsEnrichmentQuery`'s pattern with the date/description bindings) is worth a direct test mirroring `queries/historical-events.test.ts`'s existing coverage of the date-precision `OPTIONAL` logic.
- Not unit tested, consistent with every other `fetch/fetch-*.ts` pipeline entrypoint in this codebase: the live enrichment SPARQL calls and the one-off bootstrap script itself — these are network-dependent/one-shot scripts, not pure functions, and the existing pipeline doesn't unit test that class of file.

## Out of Scope

- Any rendering/UI work for the Container/nesting hierarchy — how it visually groups, indents, or collapses on the timeline is a separate, dedicated design effort (likely needing a `/prototype` detour given it's a real "what should this look like" question).
- Any Britannica scraping, source-merge/dedupe tooling, or reusable/rerunnable curated-list growth process — the curated list is supplied directly by the user this pass; growing it later, from any source, is a future effort free to design its own tooling.
- `battle`, `siege`, and `peace-treaty` as curated content — removed from the taxonomy entirely (see Implementation Decisions), not deferred. Any future need to represent a specific battle or treaty as sub-event detail is a separate future effort free to design its own mechanism.
- Nested sub-event detail generally (what a Container/sub-war's constituent battles and treaties actually look like) — this pass only proves `parentId` works structurally; it doesn't curate a battles/treaties corpus.
- Events & Inventions (Discoveries) — stays a fully separate lane, untouched by this effort beyond being the pattern this loosely mirrors.
- Any change to how `fameScore`, `Period`, or `PointInTime` work — these are already generic/shared across all four entity types (`Person`, `War`, `WarEvent`, `Discovery`); nothing about this effort changes that.

## Further Notes

- Precedent to mirror loosely: [.scratch/events-inventions-curated-source/map.md](.scratch/events-inventions-curated-source/map.md) (the Discoveries migration) and [ADR 0008](packages/data-pipeline/docs/adr/0008-discoveries-sourced-from-curated-list-not-wikidata-query.md) — the pipeline *shape* (curated file → enrichment → transform → validated output) carries over, but *what* gets curated vs. enriched differs: Discoveries curates description+date by hand, Wars enriches both from Wikidata.
- Relevant history not to repeat: [.scratch/wars-conflicts-taxonomy/map.md](.scratch/wars-conflicts-taxonomy/map.md)'s "Out of scope" section is where nesting was first deferred, and its removal of `partOfWarName` is the direct reason `parentId` needs to resolve to a real curated row rather than a free-text label.
- This spec supersedes an earlier draft of the same effort that additionally scoped a Britannica-sourced merge/dedupe tool and curator-authored descriptions/dates — both dropped from scope per direct user steer; the curated list is hand-supplied and Wikidata remains the sole source of fact for everything except identity, category, and hierarchy.
- This spec covers pipeline/schema + curation workflow only. Once curated content exists and nesting is real in the data, a follow-up spec is expected for the rendering/UI side.
