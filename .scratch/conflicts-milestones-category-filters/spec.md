# Sidebar filters: Milestone Category Group pills and a Conflicts visibility toggle

## Amendment (2026-08-12, post-implementation)

After the spec below was implemented and verified (issues 01-04, all `done`), the user asked for two follow-up changes to the Conflicts pill, both superseding text further down in this document:

1. **Standard pill convention, not an inverted toggle switch.** The Conflicts pill no longer starts pressed/active with an inverted "off means filtered" convention (contra Solution item 2, User Stories 8-9, the Implementation Decisions "Conflicts visibility toggle" bullet, and the Further Notes callout below — all now stale on this point). It now starts **unpressed** (Conflicts visible, still the same default outcome) and follows the exact same "off means unfiltered, on means narrowed" convention and visual pill styling (`OccupationDomainFilters`-style border/background, not the filled `DataDepthSwitch`-style swap) as every other sidebar pill — pressing it narrows the view by hiding every Conflict. Its `aria-label` is `"Filter by Conflicts"`, matching every other pill's `"Filter by X"` pattern (this also resolves the accessible-name collision the original `"Toggle Conflicts visibility"` label was working around — the shared "Filter by X" convention was a cleaner fix once the pill no longer needed a bespoke label).
2. **Color swatch.** The pill now renders a swatch in `CONFLICT_COLOR` (contra Solution item 2's "no color swatch" and the Implementation Decisions bullet's "no swatch"), matching every Conflict's flat rendered color on the timeline — the same "swatch matches what's already on the timeline" principle the Milestone Category Group pills use. This required relocating `CONFLICT_COLOR` from `widgets/timeline-canvas/options.ts` to `shared/config/conflict-color.ts`, since a `features/` slice can't import from `widgets/` under mini-FSD's layer rule — the same move ticket 01 made for `MILESTONE_CATEGORY_GROUP_COLORS`, for the identical reason. `ConflictsMilestonesLane.tsx` now imports `CONFLICT_COLOR` from `shared/config` instead of `./options`; its rendered value and every other consumer's behavior are unchanged.

## Amendment 2 (2026-08-12, same day, superseding Amendment 1's item 1)

Immediately after Amendment 1 landed, the user clarified further: the whole "Conflicts & Milestones" section should be **one multi-select filter**, the same shape as Region and Occupation Domain — not a Milestone Category Group filter and a separately-behaved Conflicts pill that merely render next to each other. This supersedes the entire two-control architecture described in the Solution section, User Stories, and Implementation Decisions below (Amendment 1's items are themselves now superseded by this, not just the text they originally amended):

- **One shared selection array**, `ConflictsMilestonesFilterValue[]` (`shared/config/conflicts-milestones-filter.ts`), a union of the UI-only `'conflicts'` sentinel and the 3 `MilestoneCategoryGroup` values — not two separate hook states (`useMilestoneCategoryGroupFilter` + `useConflictsVisibility`, both now deleted). One hook, `useConflictsMilestonesFilter` (`features/filter-conflicts-milestones/`), owns it — a bare `useState<ConflictsMilestonesFilterValue[]>([])` + toggle function, structurally identical to `useRegionFilter`/`useOccupationDomainFilter`.
- **One pill list component**, `ConflictsMilestonesFilters`, rendering all 4 values (Conflicts + the 3 groups) in one `<ul>`, each pill swatched, `aria-label="Filter by X"`, `aria-pressed` reflecting membership in the selection array — structurally identical to `OccupationDomainFilters`/`RegionFilters`, not a bespoke layout combining two differently-styled sub-controls.
- **Two small pure filter functions still exist** (`filterByMilestoneCategoryGroup`, `filterConflictsByFilterValues` in `map-to-items.ts`) since Conflicts and Milestones remain different data shapes in different lanes — but both now read the *same* `selectedValues` array passed down from `TimelineCanvas`'s one `selectedConflictsMilestonesValues` prop, rather than two independently-threaded props. `filterByMilestoneCategoryGroup` simply never matches the `'conflicts'` sentinel (it isn't a `MilestoneCategoryGroup`); `filterConflictsByFilterValues` checks only for the `'conflicts'` sentinel's presence, ignoring the 3 group values.
- The old `features/filter-by-milestone-category-group/` and `features/filter-conflicts-visibility/` slices (and their `MilestoneCategoryGroupFilters`/`ConflictsVisibilityToggle` components) were deleted outright, not deprecated in place — nothing referenced them once `Sidebar.tsx`/`App.tsx`/`TimelineCanvas.tsx` were rewired to the single filter.
- Net effect for a user: clicking "Conflicts" and "Technology & Industry" together shows every Conflict (subject to Region/Fame Score) plus only Technology & Industry milestones — both pills visibly pressed in the identical style, in one list, exactly like selecting two Occupation Domain pills at once.

The rest of this document (Problem Statement onward, including Amendment 1 above it) is left as originally written — the historical decision record — rather than rewritten in place. Read both amendments first; treat the Solution/User Stories/Implementation Decisions sections below as describing the *problem* and *intent* accurately but the *two-control architecture* as superseded.

## Problem Statement

The sidebar can already narrow People by Occupation Domain and narrow all three lanes by Region and Fame Score, but Conflicts and Milestones have no way to be narrowed by their own subject matter. A user who wants to see just, say, the Technology & Industry milestones, or wants Conflicts out of the way entirely while browsing Milestones, has no control for either — the merged Conflicts+Milestones lane shows everything or nothing (via the existing lane-wide fame floor) with no finer cut.

## Solution

Two additions to the sidebar, grouped in one new "Conflicts & Milestones" section (following Data Depth → Region → People in the existing order):

1. **A Milestone Category Group filter.** Three toggle pills — Knowledge & Culture, Technology & Industry, Society & Governance — each colored with the same swatch the Milestones lane already renders that group in. Clicking a pill toggles that group in/out of the Milestones lane (multi-select OR; no pills active means unfiltered, matching every other multi-select filter in the sidebar). This is the literal "same as color grouping" the feature was asked for: Milestones' color has only ever varied at the 3-group level, not the 20-leaf-category level, so filtering at that same 3-group level is both what the color already communicates and a far more usable control than 20 individual checkboxes.
2. **A Conflicts visibility toggle.** One plain pill, labeled "Conflicts", no color swatch. Conflicts carry no color-driving grouping at all (every Conflict already renders in one flat color, `CONFLICT_COLOR`, regardless of `ConflictCategory` — see `CONTEXT.md`'s Conflict Category entry and `docs/adr/0002-milestone-category-group-conflicts-blanket-toggle.md`), so there's no group structure to filter by. Rather than inventing one, or filtering by the 6 raw `ConflictCategory` values, this ships as a single blanket show/hide for the entire Conflicts lane. Unlike the other pills in the sidebar, it starts **pressed/active** (Conflicts visible, matching today's unfiltered behavior) — clicking it once hides every Conflict; clicking again restores them.

Both combine with AND against the existing Region and Fame Score/Data Depth filters, and with each other — same combination rule the whole sidebar already follows. This is a UI-only change: no new data fields, no pipeline changes, no change to `packages/shared-types/src/data/*.json`. `CONTEXT.md`'s glossary and `docs/adr/0002-...md` (both written during the grilling session that produced this spec, 2026-08-12) already document the resolved vocabulary — **Milestone Category Group** and its relationship to **Milestone Category**, and why Conflicts has no equivalent.

## User Stories

1. As a user browsing the Milestones content in the timeline, I want to click a Milestone Category Group pill (e.g. "Technology & Industry"), so that I can see only milestones in that group.
2. As a user, I want to click multiple Milestone Category Group pills at once (e.g. "Knowledge & Culture" and "Society & Governance" together), so that I can see a broader slice than one group without going back to unfiltered.
3. As a user with no Milestone Category Group pills active, I want to see every milestone regardless of group, so that the filter is opt-in and never silently hides everyone by default.
4. As a user, I want each Milestone Category Group pill's swatch to match the exact color that group's milestones already render in on the timeline, so that the filter reads as an honest, truthful legend rather than an arbitrary new color scheme.
5. As a user, I want an active Milestone Category Group pill to look visibly different from an inactive one (not just relying on the swatch color), so that I can tell at a glance which groups are currently filtering the view.
6. As a user, I want to click the "Conflicts" pill and see every Conflict disappear from the timeline, so that I can focus entirely on Milestones (and People) when I don't care about wars and revolutions right now.
7. As a user who has hidden Conflicts, I want to click the "Conflicts" pill again and see every Conflict reappear (subject to whatever Region/Fame Score/Data Depth filters are already active), so that hiding them is never a one-way trip.
8. As a user opening the app for the first time, I want the "Conflicts" pill to already show as active/pressed and every Conflict visible, so that this feature doesn't change anyone's first impression of the app.
9. As a user, I want the "Conflicts" pill to look and behave like a toggle (clearly pressed vs. unpressed), not like the other pills' "off means unfiltered, on means narrowed" convention, so that its one-control, all-or-nothing nature is obvious rather than confusing.
10. As a user, I want the Milestone Category Group filter and the Conflicts toggle to act completely independently, so that hiding Conflicts never affects which Milestones are visible, and filtering Milestones by group never affects Conflicts.
11. As a user, I want the Milestone Category Group filter to apply only to Milestones (Conflicts don't gain any per-category granularity from this feature), so that the two lanes' filters aren't confused for one another.
12. As a user, I want the Milestone Category Group filter, the Conflicts toggle, Region, and Fame Score/Data Depth to all combine with AND, so that turning on more filters only ever narrows the view further, never surprises me by adding entries back.
13. As a user filtering Milestones to "Technology & Industry" while also having selected "Europe" in the Region filter, I want to see only milestones that are both Technology & Industry *and* tagged Europe, so that the two filters compose predictably.
14. As a user, I want my Milestone Category Group and Conflicts-visibility selections to reset when I reload the page, so that this feature's state behaves exactly like every other sidebar filter (session-only, no persistence to reason about).
15. As a user, I want the new "Conflicts & Milestones" sidebar section to sit alongside Data Depth, Region, and People in a consistent visual style, so that the sidebar reads as one coherent set of controls rather than a bolted-on extra.
16. As a keyboard/screen-reader user, I want every new pill (the 3 Milestone Category Group pills and the 1 Conflicts pill) to be reachable and operable without a mouse, with a clear accessible name and current pressed state announced, so that the sidebar stays fully usable without vision.
17. As a maintainer, I want the Milestone-leaf-category-to-group mapping to live in exactly one place that both the timeline's color logic and this new filter read from, so that the two can never silently drift apart (e.g. a category recolored into a different group without the filter following).
18. As a maintainer, I want the new filtering logic expressed as small, pure, independently-testable functions (mirroring the existing `filterByRegion`/`filterByOccupationDomain`/`filterByFameScore`), so that filter correctness can be verified without rendering anything.
19. As a maintainer, I want no new data pipeline fields or JSON schema changes for this feature, so that it stays a pure `packages/web` + `packages/shared-types` type change, consistent with "the data is what the pipeline already ships."
20. As a maintainer reading `ConflictsMilestonesLane.tsx` or `options.ts` after this change, I want `MILESTONE_CATEGORY_COLORS`'s existing public shape and values to be unchanged (still one hex per leaf `MilestoneCategory`), so that this feature doesn't ripple into an unrelated rendering-code diff.
21. As a maintainer, I want a nested Conflict's visibility to never partially decouple from its Container's (per `CONTEXT.md`'s Container entry), so that hiding/showing Conflicts never leaves an orphaned child visible under a hidden parent or vice versa — trivially true here since the Conflicts toggle is all-or-nothing across the whole lane, not per-category or per-row.

## Implementation Decisions

**Milestone Category Group (new shared type):**
- New `MilestoneCategoryGroup` type + `MILESTONE_CATEGORY_TO_GROUP: Record<MilestoneCategory, MilestoneCategoryGroup>` map added to `packages/shared-types`, alongside the existing `MilestoneCategory`/`MILESTONE_CATEGORIES`. Three kebab-case values: `knowledge-culture`, `technology-industry`, `society-governance` — matching this repo's existing enum-naming convention. This is the single canonical source both the timeline's color mapping and the new filter read from, replacing the grouping that today exists only as three unexported local color constants in `packages/web/src/widgets/timeline-canvas/options.ts`.
- `options.ts`'s `MILESTONE_CATEGORY_COLORS` (still `Record<MilestoneCategory, string>`, still the same 20 keys and 3 distinct hex values it has today) becomes *derived*: compose `MILESTONE_CATEGORY_TO_GROUP` with a new, now-exported `MILESTONE_CATEGORY_GROUP_COLORS: Record<MilestoneCategoryGroup, string>` (the same 3 hexes, `#4B4597`/`#008456`/`#BC8118`, now addressable by group key instead of only existing as unexported constants). `ConflictsMilestonesLane.tsx` and every existing consumer of `MILESTONE_CATEGORY_COLORS` needs no changes — the export's shape and values are identical, only its internal derivation changes.
- New `shared/config/milestone-category-group.ts` (mirroring `occupation-domain-colors.ts`'s shape) exporting `MILESTONE_CATEGORY_GROUP_LABELS: Record<MilestoneCategoryGroup, string>` (`"Knowledge & Culture"`, `"Technology & Industry"`, `"Society & Governance"` — the exact names already used in `docs/design-tokens.md`'s table) for the pill UI, re-exported from `shared/config`'s barrel.

**Milestone Category Group filter:**
- New pure function `filterByMilestoneCategoryGroup<T extends { category: MilestoneCategory }>(items: T[], selectedGroups: MilestoneCategoryGroup[]): T[]`, added alongside `filterByRegion`/`filterByOccupationDomain`/`filterByFameScore` in `timeline-canvas/map-to-items.ts`. Empty `selectedGroups` returns `items` unchanged (unfiltered). Non-empty: keeps items whose `MILESTONE_CATEGORY_TO_GROUP[item.category]` is in the selected set (OR).
- New feature slice `features/filter-by-milestone-category-group/` (`model/useMilestoneCategoryGroupFilter.ts` owning `selectedGroups: MilestoneCategoryGroup[]` + a toggle setter, a bare `useState` mirroring `useRegionFilter`/`useOccupationDomainFilter`; `ui/MilestoneCategoryGroupFilters.tsx` rendering the 3 pills with swatch + label + `aria-pressed`, mirroring `OccupationDomainFilters.tsx`'s shape exactly).

**Conflicts visibility toggle:**
- New pure function `filterByVisibility<T>(items: T[], visible: boolean): T[]` (generic, not Conflict-specific — returns `items` unchanged when `visible` is `true`, `[]` otherwise), added alongside the other filter functions in `map-to-items.ts`.
- New feature slice `features/filter-conflicts-visibility/` (`model/useConflictsVisibility.ts` owning `conflictsVisible: boolean`, defaulting `true`, + a toggle setter; `ui/ConflictsVisibilityToggle.tsx` rendering the single plain pill — no swatch, `aria-pressed={conflictsVisible}`, label "Conflicts"). Kept as its own slice, separate from the Milestone Category Group slice above, since the two are different data shapes (a selected-set vs. a single boolean) despite rendering in the same sidebar section.

**Wiring:**
- `TimelineCanvas.tsx`'s existing per-lane `useMemo` filter chains extend: Milestones gets fame floor → `filterByRegion` → `filterByMilestoneCategoryGroup` (new); Conflicts gets fame floor → `filterByRegion` → `filterByVisibility` (new). People's chain is untouched. Filter order doesn't change the result (AND is commutative); this matches the existing fame-first precedent.
- Two new `TimelineCanvasProps`: `selectedMilestoneGroups: MilestoneCategoryGroup[]` and `conflictsVisible: boolean`.
- `App.tsx` lifts `useMilestoneCategoryGroupFilter()` and `useConflictsVisibility()` alongside the existing three filter hooks, passing state/setters down to both `Sidebar` (controls) and `TimelineCanvas` (application) — no shared context, no new state-management pattern, consistent with every existing filter.
- `Sidebar.tsx` gains one new `<section>`, "Conflicts & Milestones", placed after the existing "People" section, rendering `MilestoneCategoryGroupFilters` and `ConflictsVisibilityToggle` together.

## Testing Decisions

A good test here exercises observable behavior — a pure function's input/output, or a rendered component's visible state and the callback it fires on interaction — never internal implementation details. Same two seams the existing filters already established:

- **Pure filter functions** (`filterByMilestoneCategoryGroup`, `filterByVisibility`) — unit tests in `map-to-items.test.ts`, alongside the existing filter-function tests (empty-selection-means-unfiltered and OR-across-multiple-groups for the former; `true`/`false` pass-through for the latter).
- **`MILESTONE_CATEGORY_TO_GROUP`** — unit tested where it's defined in `shared-types`: every one of the 20 `MilestoneCategory` values covered, resolving to exactly one of the 3 `MilestoneCategoryGroup` values, matching the table already in `docs/design-tokens.md`.
- **`options.test.ts`'s existing `MILESTONE_CATEGORY_COLORS` tests** need updating (not just leaving alone) to reflect the new derivation — they should keep asserting the same public facts (one entry per `MilestoneCategory`, folded into exactly 3 distinct hexes, `CONFLICT_COLOR` distinct from all of them) but via `MILESTONE_CATEGORY_TO_GROUP` + `MILESTONE_CATEGORY_GROUP_COLORS` rather than the old private constants.
- **New Sidebar UI** (`MilestoneCategoryGroupFilters`, `ConflictsVisibilityToggle`) — RTL component tests mirroring `OccupationDomainFilters.test.tsx`/`RegionFilters.test.tsx`: render with given active state, assert the correct pill(s) show as active/pressed, assert clicking fires the right callback with the right argument. `ConflictsVisibilityToggle` additionally covers its inverted default (rendered pressed/active with no interaction).
- `Sidebar.test.tsx` extended the same way it already covers the other sections: the new "Conflicts & Milestones" section renders, props thread through correctly.
- No new test seam for `useMilestoneCategoryGroupFilter`/`useConflictsVisibility` themselves — consistent with existing precedent (thin `useState` wrappers are exercised through the UI components and pure functions instead).
- No end-to-end or visual-regression tests — not an existing pattern anywhere in this repo.

## Out of Scope

- Any per-category filtering for Conflicts (6 individual `ConflictCategory` pills, or a new group layer invented for Conflicts) — explicitly decided against; see `docs/adr/0002-milestone-category-group-conflicts-blanket-toggle.md`.
- Reinstating a `ConflictCategory`-keyed color palette — Conflicts stay one flat color; this feature adds a filter, not a color change.
- Filtering Milestones at the finer 20-leaf-`MilestoneCategory` level — the filter operates at the same 3-group level as color, not the leaf level.
- Persistence of filter state across reloads, or URL-shareable/deep-linkable filter state — matches every existing sidebar filter's session-only precedent.
- Any data pipeline or `packages/shared-types/src/data/*.json` schema changes.
- Sidebar responsive/mobile layout — a pre-existing, separately-flagged gap, untouched by this spec.
- Any change to the existing Occupation Domain, Region, or Fame Score/Data Depth filters' behavior.
