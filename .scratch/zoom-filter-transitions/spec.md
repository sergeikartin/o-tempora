# Zoom + Filter Transitions

**The sections immediately below (Problem Statement through Further Notes) are the formal spec for the zoom-animation portion of this effort**, produced via a `/grilling` session (`mattpocock-skills:grilling` + `mattpocock-skills:domain-modeling`) on 2026-08-15, starting from the implementation history further down this document. That history — two prior, fully-reverted zoom-animation attempts, plus the fade/row-shift transitions that already shipped — is preserved unedited below the spec; read it before implementing the tickets in `issues/`, since it documents specific failure modes and gotchas this spec's Implementation Decisions rely on.

## Problem Statement

Zooming via the `+`/`−` buttons in `TimelineCanvas.tsx` snaps `pixelsPerYear` instantly — every mark, gridline, and axis label jumps to its new position in a single frame. This reads as jarring and undercuts the product's framing as a "continuously zoomable" visualization: a user loses their visual anchor on what they were just looking at the moment they click zoom.

## Solution

Animate the existing `+`/`−` zoom buttons with a smooth eased transition instead of an instant snap, driven by a single `transform` attribute per lane/axis (not per-mark attribute writes, not CSS transitions) — the only mechanism a throwaway benchmark confirmed meets the performance bar at this app's real data density. No new zoom interactions ship; scope is strictly "make the two existing buttons animate."

## User Stories

1. As a user zooming in/out via the `+`/`−` buttons, I want the timeline to animate smoothly between zoom levels, so that I don't lose track of what I was looking at when the view rescales.
2. As a user, I want the Year Axis and gridlines to move in sync with the People/Conflicts/Milestones marks during the animation, so that nothing looks misaligned mid-zoom.
3. As a user, I want labels and dot markers to keep their natural shape and size throughout the animation, so that circles don't stretch into ellipses and text doesn't distort.
4. As a user, I want the timeline to stay centered on the same year I was looking at before I zoomed, exactly as it does today, so that zooming doesn't disorient me by jumping to a different part of history.
5. As a user who clicks `+` or `−` again while the previous zoom animation is still playing, I want the new click to smoothly retarget from wherever the animation currently is, so that rapid clicking feels responsive rather than laggy or queued.
6. As a user with `prefers-reduced-motion` enabled, I want zoom to still happen effectively instantly, so that this feature respects my system accessibility setting exactly like the existing fade/row-shift transitions already do.
7. As a user, I want zooming all the way to the minimum (10 visible years) or maximum (250 visible years) bound to animate correctly and clamp exactly like it does today, so that the animation doesn't introduce any new edge-case bugs at the bounds.
8. As a user browsing near either end of the full timeline range, I want the animated zoom to never jump to the wrong part of history, so that this feature doesn't reintroduce the scroll-clamp race bug a prior attempt shipped and reverted.
9. As a user, I want the `MountainProfile` minimap's viewport indicator to reflect the correct range once the zoom settles, even though it doesn't animate itself, so that it never shows a stale or incorrect range after a zoom action.
10. As a maintainer, I want the animation driven by a single group transform per lane/axis, not per-mark attribute recomputation, so that performance doesn't degrade as the dataset grows — a throwaway benchmark showed per-mark recompute costs 250-530ms/frame at today's worst-case density (~1,118 rows), 15-30x over the 16ms frame budget.
11. As a maintainer, I want the transform math (translate/scale from `pixelsPerYear`, and the label/dot counter-scale) expressed as small pure functions, so that they're unit-testable without rendering anything.
12. As a maintainer, I want row assignment left untouched by this feature, so that I don't reintroduce the "freeze rows mid-gesture" complexity a prior attempt needed — no longer necessary now that row assignment is static/per-item (ADR 0007).
13. As a maintainer, I want the real `pixelsPerYear`/`scrollLeft` React state to commit exactly once, at the end of the animation, deferred to a `useLayoutEffect` keyed on the state that actually drives DOM width, so that I don't reintroduce the scroll-clamp race that broke a prior attempt.
14. As a maintainer, I want mount's default-viewport positioning and zoom's re-centering to remain two distinct mechanisms, not unified under one formula, so that a future refactor doesn't accidentally break mount positioning the way a prior attempt did.
15. As a maintainer, I want no new runtime dependencies introduced (no framer-motion, no react-spring), so that this feature stays consistent with the app's existing D3-only animation infrastructure.
16. As a maintainer reading this code afterward, I want no wheel/pinch/click-to-focus zoom logic introduced alongside this feature, so that the diff stays scoped to "animate the existing buttons" and doesn't silently grow into a much larger interaction-design change.
17. As a QA/reviewer, I want the existing "zoom-in button widens rendered lines" test and its neighbors to still pass, extended rather than replaced, so that this feature is verifiably additive to existing zoom behavior, not a rewrite of it.

## Implementation Decisions

- **Scope:** only the existing `+`/`−` buttons in `TimelineCanvas.tsx` (`zoomControls`). No wheel, pinch, click-to-focus, or keyboard zoom introduced.
- **Mechanism:** a `transform="translate(tx) scale(sx)"` attribute on one wrapping `<g>` per lane (People; Conflicts+Milestones) plus equivalent handling on the Year Axis/gridlines — not a CSS `transition`/`transform` (unreliable through React's commit model, per the prior post-mortem below) and not per-mark attribute recompute (benchmarked as too slow: 250-530ms/frame at ~1,118 worst-case rows, vs. a 16ms/frame budget).
- **Driver:** a `requestAnimationFrame` loop (or `d3.timer`) computing `d3.interpolateNumber(startPixelsPerYear, targetPixelsPerYear)` eased via `d3.easeCubicInOut` (a close-enough stand-in for the existing `--motion-easing: cubic-bezier(0.4, 0, 0.2, 1)` token, which isn't directly consumable as a JS easing function), over a fixed duration longer than `--motion-duration-base` (200ms) — target ~300-400ms; the exact value is an implementation detail to tune.
- **Anchor:** re-centers on the year at viewport center, exactly matching current button behavior. No cursor-anchoring — there's no pointer-driven zoom gesture in scope.
- **Labels/dot counter-scale:** computed from the same interpolated `pixelsPerYear` value each tick (not a separately-eased CSS custom property), applied as a `transform` attribute on each label/dot's own group, anchored at its natural anchor point (a label's `text-anchor`, a dot's center) — this avoids the reciprocal-easing mismatch (`1/eased(t) ≠ eased(1/target)`) that broke a prior CSS-based attempt.
- **State commit:** the real `pixelsPerYear`/`scrollLeft` React state updates exactly once, when the animation ends — deferred via a `useLayoutEffect` keyed on the state that actually drives DOM width, never written in the same step that changes that state (the fix for the scroll-clamp race documented below).
- **Interrupt/retarget:** a new zoom click while an animation is in flight cancels the current `requestAnimationFrame` loop and starts a new one from the current interpolated `pixelsPerYear`, not the original start or stale target.
- **Row assignment:** untouched — no freezing needed, since row assignment is already static/per-item (ADR 0007), independent of zoom.
- **Reduced motion:** reuses the existing `motionDurationMs`/`--motion-duration-*` collapse-to-near-zero behavior — when the resolved duration is near 0, the animation should effectively resolve to the final state on the next tick, not run a full loop over a near-zero duration.
- **Mount vs. zoom recentering:** kept as two distinct mechanisms/effects, not unified — an explicit gotcha from the prior post-mortem below.
- **Minimap:** `MountainProfile`'s viewport indicator is not animated — it reflects the committed `pixelsPerYear`/`scrollLeft` state, updating once, at the end, same as before this feature.
- **No new dependencies:** built entirely on the existing `d3` package (already includes `d3-interpolate`, `d3-ease`, `d3-timer` as transitive deps).

## Testing Decisions

A good test here exercises observable end-state behavior — final rendered attribute values after an interaction resolves — not frame-by-frame animation timing, consistent with this codebase's existing precedent (the fade/row-shift transitions added in commit `a4ea9c7` were verified manually via Playwright during implementation, not committed as automated timing tests, since jsdom has no real rAF/paint fidelity).

- **Primary seam — `TimelineCanvas.test.tsx`:** extend the existing zoom tests ("the zoom-in button widens rendered lines; zoom-out narrows them back", "zooming does not change which entities are rendered"). New cases: final rendered positions match the target `pixelsPerYear` after the animation resolves; clicking a second time mid-animation retargets correctly (asserted via final end-state, not intermediate frames); reduced-motion resolves to the target state effectively immediately.
- **Secondary seam — `options.test.ts`:** unit-test any new pure functions (the group transform's translate/scale computation from `pixelsPerYear`, and the label/dot counter-scale value), mirroring existing coverage of `clampPixelsPerYear`/`pixelsPerYearBounds`.
- No new Playwright/e2e suite (none exists in this repo) — real-browser visual smoothness (marks/axis/gridlines genuinely gliding, not snapping) is verified manually via Chrome DevTools MCP during implementation, the same way the fade/row-shift and CSS-transition gotchas were originally diagnosed below.

## Out of Scope

- Any new zoom trigger: scroll-wheel, pinch/touch, click-to-focus-on-item, keyboard shortcuts, URL deep-linking. The `+`/`−` buttons remain the only zoom entry point.
- Animating the `MountainProfile` minimap's viewport indicator — it snaps to the final state.
- Cursor-anchored zoom — no meaning here, since there's no pointer-driven zoom gesture in scope.
- Any change to the zoom step size (`ZOOM_STEP = 0.2`) or bounds (`ZOOM_MIN_YEARS`/`ZOOM_MAX_YEARS`).
- Any change to the filter fade/row-shift transitions — already implemented, untouched by this spec.
- Adopting `d3-zoom`'s gesture/transform-behavior module — investigated during grilling and found to be a poor architectural fit (it's built around owning gesture capture and a single root transform; this app's zoom is externally button-triggered and fans out across a scroll container, multiple SVGs, and a CSS axis).
- Canvas-based rendering — investigated and rejected; would be a first-time new rendering technology introduced solely for this feature, and the group-transform approach already meets the performance bar without it.

## Further Notes

- This spec's technical approach is not a fresh design — it's the direct output of the `/grilling` session referenced above, which started from the implementation history below (an existing post-mortem documenting two prior, fully-reverted attempts at this exact feature). Read it in full for the failure history and the 7 numbered "gotchas" — they apply regardless of the specific tickets in `issues/`.
- One assumption from that history was explicitly re-tested during grilling, not just carried forward: whether per-mark attribute recompute (the "Attempt 1" documented below) might now be viable given that row assignment became static *after* that post-mortem was written (ADR 0007 removed the row-freezing blocker). A throwaway benchmark prototype (built and measured with Chrome DevTools MCP, in an isolated worktree) confirmed it is still not viable — 250-530ms/frame at today's worst-case density, worse than the original attempt's numbers. This spec's mechanism decision is evidence-based, re-verified against the current codebase, not inherited by default.

## Status: filter fade transitions and zoom animation both implemented

This is a post-mortem handoff, not a fresh spec. A prior session implemented, debugged, and ultimately reverted two different zoom-animation approaches after a long chain of layered bugs. **All code from that session has been discarded** — the working tree is back to the commit this session started from. This doc exists so the next attempt starts from the accumulated lessons instead of re-discovering them.

**Update 6 (2026-08-15):** the zoom-button animation (tickets 01-03 in `issues/`) is now implemented, following the Recommended Approach below — a `translate(tx) scale(sx)` group transform per lane/axis, driven by one `requestAnimationFrame` loop in `TimelineCanvas.tsx`, with `PeopleLane`/`ConflictsMilestonesLane`/`YearAxis` each exposing an `applyZoomTransform` imperative handle (`forwardRef`/`useImperativeHandle`) the driver calls every tick. Label/dot counter-scaling turned out not to need the anchor-coordinate math this doc's Implementation Decisions anticipated (`translate(anchorX) scale(...) translate(-anchorX)`): each mark's own `.module.css` already declares (or now declares) a `transform-box: fill-box`/`transform-origin` anchored at its natural point — the same mechanism the pre-existing hover-grow feature (`44acb4a`) relies on — so a bare `scale(1/sx, 1)` written there is exact with no anchor parameter needed, and no reciprocal-easing mismatch (recomputed from the same `sx` every tick, not a separately-eased CSS custom property). The real `pixelsPerYear`/`scrollLeft` state still commits exactly once at the end, reusing the deferred `useLayoutEffect` pattern already in place from before this feature. One real, reproducible bug was found and fixed during manual Chrome DevTools MCP verification, not caught by any automated test: **a one-frame visual flash on every zoom commit**, root-caused to exactly the "scroll mirroring lag" gotcha this doc's Key Gotcha #1 (technically the sticky-lane mirroring issue named under Attempt 1/2) already named — `container.scrollLeft` was being written directly in several places (the zoom commit, mount positioning, drag-to-pan, MountainProfile's click/drag-to-jump), while the two sticky lanes' own internal pan only followed via a `requestAnimationFrame`-throttled native `scroll` listener, one frame behind. Invisible during continuous motion (drag), but a single discrete jump (exactly what a zoom commit is) exposed it as a real flash: geometry lands instantly, the lane's own scroll offset catches up a frame later. Fixed with a `syncScrollLeft` helper that mirrors onto both sticky lanes synchronously wherever `scrollRef.current.scrollLeft` is written, not just from the throttled listener — confirmed via before/after `getBoundingClientRect()` sampling that the flash is gone and stays gone across zoom-in, zoom-out, and interrupted/retargeted zooms. Verified via Playwright-style Chrome DevTools MCP sampling (not committed as an automated timing test, consistent with this doc's own Testing Decisions): a mark's rendered position glides smoothly frame-by-frame rather than snapping, all three animated surfaces (People, Conflicts+Milestones, Year Axis/gridlines) stay in sync, min/max zoom bounds clamp correctly with no error, and a rapid double-click correctly compounds two full zoom steps with no stale-target regression.

**Update (2026-08-15):** a follow-up session re-attempted the filter fade transitions alone (enter/exit opacity, no zoom), hit a real bug (exit fades were invisible — the lane's SVG shrinks and clips them in the same commit the fade starts, since totalHeight tracks the live filtered row count), then went further upstream and fixed the root cause called out in Key Gotcha #1 below: rows are now a **static per-item identity**, computed once against the full dataset at a fixed reference scale, never the live zoom or the currently-filtered set (`packages/web/docs/adr/0007-static-row-assignment-replaces-live-per-render-packing.md`). That means **Key Gotcha #1 and Attempt 1/2's "row-freezing" workarounds (bug 2 in each) are now moot for any future zoom-animation attempt** — row assignment can't reshuffle mid-gesture because it no longer depends on zoom at all. The animation work itself (enter/exit fades, and zoom) is still unimplemented; only this one prerequisite changed.

**Update 2 (2026-08-15):** filter fade transitions are now (re-)implemented in `PeopleLane.tsx`/`ConflictsMilestonesLane.tsx`, following the "What's proven to work" section below exactly — enter/exit opacity via `.join()`'s three-callback form, `useLayoutEffect` (not `useEffect`), and `shared/lib/motion.ts`'s `motionDurationMs`. The static-row-assignment prerequisite from Update 1 turned out to still leave one live gap worth naming precisely: `totalHeight` is derived from `compactRows`, which only sees *currently-rendered* items — an item that just exited is gone from that count immediately, so the SVG's own `height` attribute can shrink in the same commit an exit fade starts. Rather than special-casing the height calculation (e.g. holding it at the max of current/previous row counts until the exit transition ends), the fix applied is simpler and fully general: both lanes' `.svg` rule now sets `overflow: visible`, so a fading-out mark below the new (shorter) height is never clipped by the SVG viewport regardless of why the height changed. Verified via a Playwright session against the running dev app: sampling `getComputedStyle(g).opacity` on `.d3-person` groups every ~40ms while toggling the People fame-score filter showed a smooth 0→1 ramp on enter and 1→0-then-removed ramp on exit, both over the expected ~200ms (`--motion-duration-base`). Zoom animation (the "Recommended approach" section below) is still unimplemented.

**Update 3 (2026-08-15):** added a row-shift transition alongside the fade — when `compactRows` re-indexes a still-visible item to a different row (because an item above/below it in the static order was filtered in or out), that item's mark now glides to its new row instead of snapping. Mechanically: each row-derived attribute (`y1`/`y2` on a line, `y` on a label, `cy` on a dot, and the hit-rect's `y`/`height`) is set instantly for a *brand-new* mark (inside the `enter` callback, so it appears already in place under the opacity fade — no unwanted slide-in-from-row-0), then set again via `.transition().duration(durationMs).attr(...)` on the full enter+update merged selection — a no-op for the just-entered mark (same value in, same value out) and a genuine interpolation for a mark that already existed at a different row. Every other attribute (`x1`/`x2`/`x`/`cx`, `fill`, `data-*`, text content) stays an instant, non-transitioned `.attr()` call, since only row (never year-position) changes with filtering — zoom is the only thing that would move x, and that's still out of scope. Verified the same way as Update 2: sampled a persisting mark's `y1` every ~25ms while toggling the Region filter and saw it interpolate smoothly across intermediate values over ~200ms, not jump directly from old to new.

**Update 4 (2026-08-15):** fixed a real, user-reported bug in Update 3's row-shift: surviving `PeopleLane` marks visibly jumped down first, then slid back up — "sliding up from the bottom" instead of smoothly moving from their real prior position. Root cause was specific to `PeopleLane` (not `ConflictsMilestonesLane`): `personLabelYForRow`/`personLineCenterYForRow` compute every row's y from `LANE_TOP_PADDING + (rowCount - 1 - row) * PERSON_ROW_PITCH` — i.e. row 0's position (and therefore *every* row's position) depends on the live `rowCount`, not just that item's own row, because row 0 is deliberately pinned to the *bottom* of the lane (closest to the Year Axis) via `.bottomAlign`'s `justify-content: flex-end`. `totalHeight` (`personLaneHeight(rowCount)`) was still a plain React-rendered `<svg height={totalHeight}>` attribute, so it snapped instantly on every filter change while the marks' own `y` attributes animated smoothly — the instant height snap moved the bottom-aligned svg's on-screen top edge immediately, and the marks' transition (still starting from their pre-snap on-screen position) then had to visibly "catch up," reading as jump-then-slide. Confirmed the mechanism algebraically before fixing: with `y = T + (rowCount - 1 - row) * P` and `totalHeight = T + rowCount * P`, transitioning `totalHeight` with the *exact same* duration and easing as the row-shift makes the `rowCount` term cancel out of the on-screen position exactly, leaving only the item's own `row` reassignment (if any) to visibly animate — a mark whose row didn't change doesn't move on screen at all, which is what "come from original position" means here. Fix: `PeopleLane.tsx` no longer sets `height` via JSX — the `<svg>`'s `height` attribute is now fully D3-owned (same pattern as every mark attribute already was), set instantly via `.attr()` on mount (tracked via a `hasMountedRef`) and via `.transition().duration(durationMs).attr('height', totalHeight)` on every subsequent update, using the identical `durationMs` the row-shift transitions use. `ConflictsMilestonesLane` didn't need this — its rows are anchored from a fixed *top* offset (independent of `rowCount`) with no bottom-align wrapper, so its `totalHeight` shrinking never moved existing content. Verified via Playwright against the live dev app: tracked a mark whose relative row was confirmed unchanged (Q6534, always at the topmost row before and after a Region-filter toggle) and its `getBoundingClientRect().y` stayed *exactly* constant (658.93px) across the entire transition — zero motion, not jump-then-settle.

**Update 5 (2026-08-15):** fixed a second user-reported symptom of Update 4's animated svg height: toggling a filter *off* (more people appear, svg grows) left a small unscrolled gap at the bottom of `.peopleLane`, closest to the Year Axis. Cause: `TimelineCanvas.tsx` pins `.peopleLane`'s scroll to the bottom (`el.scrollTop = el.scrollHeight`) in a `useLayoutEffect` keyed on `filteredPeople`, which — like every layout effect — runs in the same synchronous commit as `PeopleLane`'s own layout effect that *starts* the height transition. At that instant, `el.scrollHeight` still reflects the *pre*-transition height (the D3 transition hasn't ticked yet), so the pin lands short; as the svg keeps growing smoothly over the next ~200ms, `scrollHeight` grows past where `scrollTop` was already fixed, leaving a gap the browser doesn't auto-correct (it only clamps `scrollTop` down when `scrollHeight` shrinks, never pulls it up when `scrollHeight` grows). Fix: the same effect now also attaches a `ResizeObserver` to the `<svg>` inside `.peopleLane` (not to `.peopleLane` itself, which has a fixed flex height and never resizes) that re-applies the same pin on every layout change for as long as the observer stays attached (recreated each time `filteredPeople` changes, disconnected on cleanup) — so the pin tracks `scrollHeight` continuously through the whole transition instead of once at the start. `ResizeObserver` doesn't exist in the jsdom test environment, so the effect guards with `typeof ResizeObserver === 'undefined'`; the pre-existing instant pin still covers that case, and the existing scroll-pin test doesn't exercise the observer path at all. Verified via Playwright: sampled `scrollHeight - clientHeight - scrollTop` (the unscrolled gap) every 30ms through both a shrink (raising the fame floor) and a grow (lowering it back) — the gap stayed at ~0px throughout both, including well after settling, versus a real gap before this fix.

The original ask: smooth, non-jarring transitions when the user zooms in/out (the `+`/`−` buttons in `TimelineCanvas.tsx`) and when a filter (Fame Score, Occupation Domain, Region, Conflicts & Milestones) changes which entries are visible, across the People and Conflicts+Milestones lanes.

## What's proven to work: filter fade transitions

Standard D3 enter/exit transitions inside each lane's existing `.join()` call (`PeopleLane.tsx`, `ConflictsMilestonesLane.tsx`):

- An entering mark's `<g>` starts at `opacity: 0`, then `g.transition().duration(fadeDurationMs).style('opacity', 1)`.
- An exiting mark gets `pointer-events: none` (so a mid-fade mark can't still be clicked) and `exit.transition().duration(fadeDurationMs).style('opacity', 0).remove()`, overriding `.join()`'s default synchronous exit-removal.
- Duration from a shared `motionDurationMs('--motion-duration-base')` helper (see below).

This part worked cleanly, had no reported issues, and is independent of everything below — re-implement it first without worrying about the zoom half.

**One real bug fixed along the way, worth re-applying:** the D3-updating effects in both lane components were plain `useEffect`, which React defers until after paint. That's invisible for a single instant update but shows up as a one-frame-stale-paint flash whenever something else (like a zoom transform) changes in the same commit. Both effects should be `useLayoutEffect`, not `useEffect`.

**A small, genuinely reusable utility, worth re-adding as-is:** a `shared/lib/motion.ts` with a `motionDurationMs(token)` helper that reads a `--motion-duration-*` CSS custom property via `getComputedStyle` **once and caches it** (invalidated only on a `prefers-reduced-motion` `matchMedia` change event). A naive per-call `getComputedStyle` read showed up directly in a Chrome DevTools MCP performance trace as a "Forced reflow" source once it was being called from inside a per-frame code path — caching it is cheap insurance regardless of which zoom approach is chosen.

## What was tried for zoom, and why each attempt failed

### Attempt 1: JS-driven `d3.transition().tween()`, recomputing every mark's `x1`/`x2`/`cx` every frame

Animated `pixelsPerYear` and `scrollLeft` together via a `d3.transition()` on the scroll container, with a `.tween()` callback that ran on every animation frame: recompute the x-scale for the interpolated `pixelsPerYear`, re-derive `scrollLeft`, write both to state and to the DOM.

Getting this *correct* took several fixes:
- The two sticky lanes' (`position: sticky`) internal horizontal pan is driven by manually mirroring `scrollLeft` onto them — the existing mirror only ran from a `requestAnimationFrame`-throttled native `scroll` listener, one frame behind a per-frame-driven `scrollLeft` write.
- `assignRows` (`map-to-items.ts`) packs items into rows by **pixel** overlap (a label's rendered width is fixed in pixels regardless of zoom), so row assignment is genuinely zoom-level-dependent — recomputing it every animation frame reshuffled items between rows dozens of times over one zoom gesture. Had to freeze row layout during the animation and only let it settle once, at the end.
- The `useLayoutEffect` bug above (marks lagging a frame behind a synchronously-written `scrollLeft`).

Even after all of that, a Chrome DevTools MCP performance trace showed the fundamental problem: recomputing and writing every mark's geometry attributes on every frame cost **30–90ms per frame** of real DOM/layout/paint work (worse in dev-mode React, present in a production `vite preview` build too). CLS (Cumulative Layout Shift) measured 0.78–0.82 during a single zoom click. Not fixable by chasing individual bugs — the *approach* doesn't scale with mark count.

### Attempt 2: CSS `transform: scaleX(...)` "preview", then one atomic commit to the real layout

The idea: fake the zoom visually with a single cheap `transform: scaleX(ratio)` applied to the gridlines, Year Axis, and each lane's `<svg>` root (anchored via `transform-origin` at the year currently at viewport center), let a CSS `transition` animate it on the compositor (~zero JS cost regardless of mark count), then swap it for the real, precisely-recomputed `xScale` in one atomic commit once the transition ends. Verified mathematically that a plain `scaleX` anchored correctly, with `scrollLeft` held fixed during the preview, is *exact* — not an approximation — for "zoom around the point at viewport center."

This is the right idea in principle (see Recommended Approach below for the fix), but the concrete implementation accumulated bugs faster than they could be closed out, in roughly this order:

1. **Scroll mirroring lag** — same sticky-lane mirroring issue as Attempt 1, fixed the same way (a shared `syncScrollLeft` helper called synchronously wherever `scrollLeft` changes, not just from the throttled native listener).
2. **Row packing reshuffling** — same issue as Attempt 1. Fixed by giving the lanes a second `rowScale` prop, frozen at the *target* zoom level and updated only once the CSS transition's `'end'` event fires — later simplified away entirely once positions and rows started updating atomically at commit (see point 4).
3. **`useLayoutEffect` vs `useEffect`** — same fix as above; more critical here because the commit's `scrollLeft` write is a direct synchronous DOM mutation racing a *deferred* passive-effect mark update, which read as "everything visibly slides in the wrong direction for an instant, every frame" (scrollLeft moves opposite the pan direction, so a scrolled-but-not-yet-repositioned frame looks like content sliding backwards).
4. **Scroll-clamp bug** — a real, reproducible, user-visible bug: the commit set `scrollLeft` to a value computed for the *new*, wider scale, but the DOM elements hadn't actually been resized to that width yet (React hadn't re-rendered). The browser silently clamps an out-of-range `scrollLeft` write to the *still-old*, narrower `scrollWidth` — landing the commit hundreds of years off from where the user actually was, worse the further back from "today" the user was centered (which is exactly why it reproduced at "zoomed in around 1800" specifically — the further the center year from the timeline's other end, the more room for the old/new `scrollWidth` gap to exceed the intended `scrollLeft`). Root cause: `commitZoom` set `scrollLeft` in the same synchronous step as the state change that would eventually widen the DOM, instead of waiting for that widening to actually land.
   - Fix pattern: never write `scrollLeft` in the same function/step that also changes `pixelsPerYear`. Stash the target year in a ref, and apply it from a `useLayoutEffect` keyed on the state (`pixelsPerYear`/`scale`) that actually drives the DOM width — that effect only runs *after* the re-render has landed.
   - **This same class of bug existed at *mount* too** (the original "pan to `DEFAULT_VIEWPORT_START`" code), and a later refactor that tried to unify the mount case and the zoom-recenter case under one "recenter on this year" formula broke mount positioning, because the two have different semantics: mount wants `DEFAULT_VIEWPORT_START` at the viewport's **left edge** (`scrollLeft = scale(year)`, no adjustment), while a zoom commit wants a year **centered** (`scrollLeft = scale(year) - clientWidth / 2`). Keep these as two distinct pending-ref mechanisms (or two distinct effects) even though the timing fix (defer until the real re-render lands) is shared — don't collapse them into one formula.
5. **Labels and dots visually squished** — a bare ancestor `scaleX` doesn't just reposition its children, it stretches their own rendering non-uniformly (text glyphs, circle markers). Fixed by cascading a `--zoom-preview-inverse-scale-x` CSS custom property (`1 / scaleX`) that each label/dot applies as its own local counter-`scaleX`, anchored at its own natural anchor point (a label's `text-anchor`, a dot's center), composed with the existing hover-scale via a second custom property in the same `transform` value (`scaleX(var(--zoom-preview-inverse-scale-x, 1)) scale(var(--hover-scale, 1))`) rather than two competing `transform` declarations.
6. **The CSS transition never actually animated at all** — this is the one that ended the attempt. Verified directly (see "Key gotcha" below) that setting a `transition` declaration and a new `transform` value in the *same* style write never animates in this browser, no matter how it's triggered from React — not via a single render, not via `flushSync` + a forced synchronous reflow (`element.offsetWidth`) between two *separate* `flushSync`-wrapped writes, not via a single `requestAnimationFrame` gap between the two writes. The only technique that verified reliably (confirmed against a raw, non-React DOM element first) was a **double** `requestAnimationFrame`: render at identity (`scaleX(1)`, transition established, no value change yet), wait two full animation frames, *then* render the real target. Once that was wired up, the outer `scaleX` genuinely animated smoothly — but the labels' counter-scale (driven by the custom property, going through its own always-on CSS `transition`) turned out **not** to be reliably synchronized with it frame-by-frame, for two compounding reasons: (a) a real duration mismatch if the label's own transition uses a different token than the outer transform's, and (b) even with matched durations, `1 / eased(t)` (what the outer scale's reciprocal actually is at each instant) is not the same function as `eased(1/target)` (what a naively-configured counter-transition on the label produces) — they only agree at the two endpoints, not in between. This was flagged as a real residual sync issue (visible as label "wobble") that the session ran out of time to fully resolve before the whole approach was reverted.

### Why the whole CSS-transform attempt is not recommended as-is

Beyond the specific bugs above, two structural problems make this approach fragile even once "working":

- CSS's transition-triggering behavior through React's rendering/batching model was unreliable and required an undocumented, easy-to-regress two-frame delay trick to get *any* animation out of it at all — not something to depend on without very defensive testing.
- The label counter-scale's reciprocal-easing mismatch (point 6 above) is a genuine mathematical property of the technique (`1/eased(t) ≠ eased(1/target)`), not a bug that can be patched away without either (a) computing the label's counter-scale from the outer transform's *actual current value* each frame (which requires reading it back — `getComputedStyle`, itself a forced-reflow source — or driving both from the same JS-computed value, at which point you're not really using CSS transitions for the timing anymore), or (b) accepting the mismatch as a minor, brief visual imperfection.

## Recommended approach: drive it with D3, via an SVG `transform` attribute, not CSS

Apply a single `transform="translate(tx) scale(sx)"` **attribute** (not a CSS `style`/`transform` property) to one wrapping `<g>` per lane (and equivalent handling for the gridlines/Year Axis), updated every frame via `d3.interpolate` + a JS timer (`d3.timer` or a plain `requestAnimationFrame` loop) — the same *mechanism* as Attempt 1's per-frame tween, but updating **one group transform**, not every mark's own `x1`/`x2`/`cx`. This keeps the O(1)-per-frame cost that made Attempt 2 attractive, while sidestepping CSS's transition-triggering fragility entirely, because you're not relying on a CSS `transition` to interpolate anything — the interpolation is plain JS math, computed and written every frame, same as Attempt 1's tween but touching one node instead of hundreds.

Concretely:
- Compute `centerYear` the same way both prior attempts did (`scale.invert(scrollLeft + clientWidth / 2)`).
- On each tick (`d3.interpolateNumber(startPixelsPerYear, targetPixelsPerYear)` fed through the existing `--motion-easing` cubic-bezier, or `d3.easeCubicInOut` as a close-enough stand-in), compute the group's `translate`/`scale` values *and* the label counter-scale value from the **same** interpolated `pixelsPerYear`, in the same tick — this is what makes the label counter-scale exact rather than approximated, unlike Attempt 2's CSS-custom-property version. Apply the counter-scale as a `transform` attribute on the label group too (or a nested `<g>` around just the label), also computed that same tick.
- Still hold `scrollLeft` fixed during the animation and fold the pan into the group's own translate, exactly like Attempt 2's `transform-origin` trick (the math worked; keep it) — this still avoids the old Attempt-1 problem of re-deriving and writing `scrollLeft` every frame.
- At the end of the tick sequence, do the one real commit: set `pixelsPerYear`/`scrollLeft` state to the precise final values (through the deferred-until-DOM-actually-widens pattern from bug 4 above), and reset the group transform to identity in the same commit.
- Row-freezing (bug 2) still applies regardless of animation mechanism — freeze row assignment at the start of the gesture, only let it settle once, at the true end.

## Key gotchas (apply to any future attempt, whichever mechanism is chosen)

1. **`assignRows` (`map-to-items.ts`) is pixel-space-dependent.** A label's rendered width doesn't scale with zoom, so which items collide is genuinely a function of the current zoom level. Any animated zoom must freeze row assignment for the duration of a gesture and only let it settle once, at rest — not recompute it every frame/tick.
2. **Never write `scrollLeft` for a target zoom level before the DOM has actually been resized to that level's width.** The browser silently clamps an out-of-range `scrollLeft` assignment to the current (stale) `scrollWidth`, with no error — this produced a real, reproducible, hard-to-notice-in-testing bug (lands hundreds of years off). Always defer the `scrollLeft` write to a `useLayoutEffect` keyed on whatever state actually drives the DOM width, never in the same step that changes that state.
3. **Mount's default-viewport positioning and zoom's re-centering are not the same operation** — one left-aligns a year, the other centers a year. Don't unify them under one formula even if the *timing* fix (defer until the real width lands) is shared between them.
4. **A CSS `transition` declaration and a new value for the property it watches, set in the same style write, will not animate** — confirmed repeatedly, including via `flushSync` + a forced synchronous reflow between two separate writes, which is the standard textbook fix and still didn't reliably work when driven from inside a React event handler. A double-`requestAnimationFrame` gap between the "establish transition" write and the "set target value" write was the only technique that verified reliably. This is exactly why the Recommended Approach above sidesteps CSS transitions altogether rather than fighting this further.
5. **`transform: scaleX(...)` (or any non-uniform scale) on an ancestor visually distorts circles into ellipses and stretches text glyphs**, not just repositions them — anything that should keep its own shape (labels, dot markers) needs an explicit local counter-scale, anchored at its own natural anchor point (a label's `text-anchor`, a circle's center).
6. **CLS (Cumulative Layout Shift), as reported by a Chrome DevTools MCP performance trace, is not a reliable signal that a CSS-transform-based animation is actually animating.** CSS transforms don't affect layout by spec, so the Layout Instability API doesn't register them at all — a trace can report CLS: 0.00 whether the transform is genuinely interpolating smoothly *or* snapping instantly with no animation whatsoever. To verify an animation is actually happening, sample `getComputedStyle(element).transform` (or the relevant property) at intervals during the transition and check it's actually changing, don't rely on CLS alone.
7. **A performance trace's "Forced reflow" insight is worth taking seriously but double-checking its line attribution** — one session's trace attributed reflow time to a pure data-filtering function with zero DOM access, almost certainly a source-map/dev-transform artifact rather than a real bug in that function. Don't chase a fix for a location that structurally can't be the cause.
