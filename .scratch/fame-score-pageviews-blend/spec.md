# Wars & Discoveries: blend sitelinks and pageviews into fameScore

## Problem Statement

Wars & Discoveries' `fameScore` is raw Wikidata sitelink count — a single signal, unlogged, unblended, per `rankBySitelinks`'s own "never blended" design comment. Sitelinks capture how many language editions bothered to write an article at all, but not sustained real-reader interest: a topic can accumulate sitelinks purely from stub-quality coverage across many small wikis while a topic like World War II, read constantly, is capped by the same linear count as anything else. This makes fameScore a weaker density/comparability signal than it could be for the one thing it actually drives — the sidebar's manual fame-floor filter (`FAME_SCORE_BOUNDS`/`FameScoreFilters`, ADR 0003) — and for cross-lane comparability between a war's and an invention's score.

[ADR 0010](../../packages/data-pipeline/docs/adr/0010-blend-sitelinks-and-pageviews-for-wars-discoveries-fame-score.md) has already decided the fix and is `Status: accepted`. `CONTEXT.md`'s pending diff already documents the new Fame Score definition. The pipeline code (`score.ts`, the fetch stages, `write-datasets.ts`, `FAME_SCORE_BOUNDS`) does not yet implement it — `rankBySitelinks` still ranks by raw sitelinks alone. This spec is that implementation.

## Solution

Implement ADR 0010's formula exactly as decided:

```
fameScore = round(0.60 * S_sitelinks + 0.40 * S_pageviews)
S_sitelinks = min(100, 100 * ln(1 + sitelinks) / ln(1 + 350))
S_pageviews = min(100, 100 * ln(1 + pageviews) / ln(1 + 200_000_000))
```

`pageviews` is the sum of per-article monthly Wikimedia pageviews across a fixed 7-language basket (en/zh/es/fr/de/ar/ru), over the trailing 4 full calendar years, via the Wikimedia Pageviews REST API's per-article endpoint. A language with no sitelink for a given entity, or a missing/redirected title, contributes 0 pageviews for that language — best-effort, no redirect-resolution logic. A pageviews-fetch failure degrades the entity's `S_pageviews` to 0 rather than dropping the row (mirrors the ADR's rejected-options rationale: pageviews is a secondary signal, and the curated list is the sole inclusion gate per ADR 0008/0009). A sitelinks-fetch failure (`sitelinks` unresolved) still drops the row entirely at Output, unchanged from today — Wikidata not knowing the entity at all is a harder failure than a stalled secondary API call.

This only touches Wars & Discoveries. People's Pantheon HPI scoring (`scoreAndRankByHpi`, `FAME_TIER_MIN_HPI`) is untouched — "never blend across lanes" still holds, only "never blend within a lane" is overridden, and only for these two.

## User Stories

1. As an app visitor filtering Wars & Conflicts or Discoveries & Inventions by the sidebar's fame-floor slider, I want the floor to reflect both how widely-documented and how widely-read an entity is, so that a heavily-visited topic like World War II isn't ranked behind a topic that merely accumulated more stub articles.
2. As an app visitor comparing a war's fame against an invention's fame, I want both lanes scored on the same 0–100 scale from the same formula, so that the two lanes stay directly comparable, matching how they already share one sidebar filter mental model.
3. As a developer running the pipeline, I want a new fetch stage that resolves each curated Wars/Discoveries QID's sitelink article titles in the 7-language basket and sums their trailing-4-year monthly pageviews, so that `S_pageviews` has real data to compute from.
4. As a developer, I want the per-language title lookup added as new `OPTIONAL` bindings on the existing per-QID wars/events enrichment SPARQL queries (extending the pattern the existing English `?article` binding already uses, one `OPTIONAL` block per language), rather than a second SPARQL pass, so that title resolution reuses the enrichment pass already keyed on curated ids instead of adding a third fetch stage per lane.
5. As a developer, I want a new pageviews REST client module, structurally parallel to `commons-client.ts` (own endpoint constant, courtesy `User-Agent`, retry-on-429/502-504 with backoff, `AbortSignal.timeout`), so that the new network boundary follows the same resilience conventions every other external call in this pipeline already does.
6. As a developer, I want the pageviews fetch stage to run after `fetchWarsEnrichment`/`fetchEventsEnrichment` (it depends on their now-widened enrichment output for titles) and to write its own raw file, mirroring how `fetchImageAttribution` depends on and runs after the same two stages, so that raw-file dependency ordering in `fetch/index.ts` stays legible.
7. As a developer, I want `score.ts` extended with a new pure blend function implementing the formula above, alongside the existing `rankBySitelinks`/`scoreAndRankByHpi`, so that the scoring seam stays a pure, directly unit-testable function like its siblings.
8. As a developer, I want `rankBySitelinks` removed once the new blend function replaces its only two call sites (`transformWars`/`transformDiscoveries`), so that dead code implementing the now-superseded sitelinks-only ranking doesn't linger.
9. As a developer, I want `transformWars`/`transformDiscoveries` to read the new pageviews raw file (keyed by curated id, same convention as `image-attribution.raw.json`'s `wars`/`discoveries` keys) and pass each row's `sitelinks` + `pageviews` into the new blend function, so that Transform's existing group→tag→score shape is preserved, just with a richer score input.
10. As a developer, I want `buildWars`/`buildDiscoveries` in `write-datasets.ts` to read `fameScore` from the row's now-blended value instead of raw `sitelinks`, while keeping the existing `row.sitelinks <= 0` drop gate unchanged, so that the enrichment-failure drop semantics (sitelinks failure = Wikidata doesn't know the entity) stay exactly as they are today.
11. As a developer, I want `FAME_SCORE_BOUNDS` for `wars`/`discoveries` in `viewport.ts` moved from lane-specific raw-sitelink ranges to one shared 1–100 range with default 75 (per the ADR's documented consequence), so that the sidebar filter's bounds match the new score's actual scale rather than a stale raw-count range.
12. As a developer, I want the exact constants (350, 200,000,000, 0.60, 0.40, the 7-language basket, the 4-year window) recorded as inline comments in `score.ts`/the new fetch stage next to the blend function, not in `docs/config-variables.md`, so that they're discoverable at the point of use and correctly scoped as fixed pipeline constants (require a code change + pipeline re-run to alter) rather than runtime-tunable config.
13. As a developer re-running the pipeline after this change, I want `npm run fetch`, `npm run build-data`, and `npm run publish-data` to produce a complete, valid dataset with the new blended scores end to end, so that the ADR's decision is actually live in the shipped app, not just implemented in isolated modules.
14. As the maintainer of `CONTEXT.md`, I want no further changes needed there — the pending diff already documents Fame Score's new definition — so that this implementation lands consistent with docs that were updated ahead of the code.

## Implementation Decisions

- **`score.ts`**: add a new pure function (parallel to `rankBySitelinks`/`scoreAndRankByHpi`) that computes `fameScore` per the formula above from `{ sitelinks, pageviews }` and sorts descending by the result — same signature shape and no-floor behavior `rankBySitelinks` has today (curated lists need no floor-filtering, per the existing header comment, which carries over). `rankBySitelinks` is removed once both call sites migrate. `FAME_TIER_MIN_HPI`/`scoreAndRankByHpi` are untouched.
- **Enrichment query widening**: `buildWarsEnrichmentQuery`/`buildEventsEnrichmentQuery` each get 6 new `OPTIONAL` blocks (zh/es/fr/de/ar/ru), structurally identical to the existing English `?article` binding (`schema:about ?event; schema:isPartOf <https://{lang}.wikipedia.org/>`), each bound to its own `?articleZh`/`?articleEs`/etc. variable. `EnrichedWar`/`EnrichedEvent` (and their `isEnrichedWar`/`isEnrichedEvent` boundary validators) gain an optional per-language title map or a small set of optional per-language fields — implementer's choice, but validated at the boundary the same way every other enrichment field already is.
- **New fetch stage** (e.g. `fetch-pageviews.ts`, peer to `fetch-image-attribution.ts`): reads `wars-curated-enriched.raw.json` and `events-curated-enriched.raw.json` (now carrying per-language titles), and for every curated id, fetches trailing-4-year monthly pageviews per resolved-language title via the new client, sums across languages, and writes a raw file keyed the same way `image-attribution.raw.json` is (`{ wars: Record<id, number>, discoveries: Record<id, number> }`). Missing title for a language contributes 0. Ordered in `fetch/index.ts` after `fetchWarsEnrichment`/`fetchEventsEnrichment`, same dependency shape `fetchImageAttribution` already has on those two.
- **New pageviews REST client** (peer to `commons-client.ts`): wraps `https://wikimedia.org/api/rest_v1/metrics/pageviews/per-article/{project}/all-access/all-agents/{article}/monthly/{start}/{end}` (compact `YYYYMM01` start/end format, `{project}` = `en.wikipedia`/`zh.wikipedia`/etc., article title with underscores). Same courtesy `User-Agent`, same 429/502-504 retry-with-backoff treatment as `commons-client.ts`/`wikidata-client.ts`. A 404 (no pageview data for that title/period) is treated as 0 pageviews, not an error — a real, expected response shape for a low-traffic or newer article, not a transient failure to retry.
- **Trailing 4-year window**: computed from the pipeline run's current date at fetch time — the 4 most recently *completed* calendar years (excludes the current partial year), consistent with the ADR's benchmark-derivation pilot. Not configurable.
- **Batching/pacing**: one pageviews REST call per (curated id × resolved language), no VALUES-clause batching available (this is a REST API, not SPARQL) — paced with the same kind of `BATCH_DELAY_MS`-style courtesy delay `batched-sparql-fetch.ts` and `batched-commons-image-attribution-fetch.ts` already use between request groups, sized for however many total calls the ~275-entity curated set × up to 7 languages produces.
- **`transformWars`/`transformDiscoveries`**: load the new pageviews raw file the same way `loadImageAttributionFile` is loaded today, and pass `{ sitelinks: row.sitelinks ?? 0, pageviews: pageviewsById[row.id] ?? 0 }` into the new blend function in place of the `rankBySitelinks` call.
- **`write-datasets.ts`**: `buildWars`/`buildDiscoveries` read `fameScore: row.fameScore` (the already-blended value from Transform) instead of `fameScore: row.sitelinks`. The `row.sitelinks <= 0` drop check is unchanged — it gates on sitelinks specifically, not the blended score, per the ADR's rejected-options rationale on pageviews-failure handling.
- **`FAME_SCORE_BOUNDS`** (`packages/web/src/shared/config/viewport.ts`): `wars`/`discoveries` move to `{ min: 1, max: 100, default: 75 }` each, per the ADR's documented consequence — a provisional value to be manually re-tuned once real scores are visible in the running app, not precisely re-derived here.
- **Constants placement**: 350, 200,000,000, 0.60, 0.40, the 7-language basket, and the 4-year window live as inline comments in `score.ts` next to the new blend function (mirroring `FAME_TIER_MIN_HPI`'s existing derivation-comment convention) — not in `docs/config-variables.md`.

## Testing Decisions

- Good tests here exercise the same two seams `score.test.ts` and `commons-client.test.ts` already establish as this pipeline's pattern: pure formula correctness on one side, mocked-fetch/retry behavior on the network boundary on the other. Neither seam should assert on implementation details (query string construction, exact request pacing) beyond what's already asserted for their siblings.
- **`score.test.ts`**: extend with cases for the new blend function — known sitelinks/pageviews pairs producing the documented formula's output (including the two clamp-at-100 edges for each component), a missing/zero pageviews input still producing a valid score from sitelinks alone, sort order (descending by blended score), and no-floor behavior (every row kept, mirroring `rankBySitelinks`'s existing "keeps every row" test). Confirm the log-scale monotonicity property (higher sitelinks or higher pageviews never decreases the score) rather than hardcoding every intermediate float.
- **New pageviews-client test file**, mirroring `commons-client.test.ts`: asserts the correct endpoint URL shape (project/article/date range) is requested, a successful response is parsed into a pageviews total, a 404 is treated as 0 rather than thrown, and 429/502-504 responses retry with backoff before succeeding — same `flushRetries`/mocked-`globalThis.fetch` pattern `commons-client.test.ts` and `wikidata-client.test.ts` already use.
- **`transform/index.test.ts`**: extend `transformWars`/`transformDiscoveries` cases (or add them if they don't already cover this) with a synthetic pageviews raw fixture, asserting the row's final `fameScore` matches the blend function's output for that row's sitelinks/pageviews pair.
- **`write-datasets.test.ts`**: extend `buildWars`/`buildDiscoveries` cases asserting `fameScore` in the built entry equals the row's already-blended input value (not re-derived from sitelinks), and that the `sitelinks <= 0` drop still fires regardless of a nonzero blended score.
- Not unit tested, consistent with every other `fetch/fetch-*.ts` pipeline entrypoint in this codebase: the new fetch stage's own orchestration script (`fetch-pageviews.ts` or equivalent) and the live enrichment SPARQL calls — network-dependent orchestration, not pure functions, and the existing pipeline doesn't unit test that class of file. The query-builder widening itself (new `OPTIONAL` blocks) is worth a direct test only if `wars-enrichment.ts`/`events-enrichment.ts` already have query-builder test coverage today — extend that if it exists rather than introducing a new query-testing convention for this change alone.

## Out of Scope

- Any change to People's Pantheon HPI scoring, `FAME_TIER_MIN_HPI`, or `scoreAndRankByHpi` — untouched by this effort.
- Any change to what `fameScore` is allowed to drive downstream — still only the manual UI filter floor (ADR 0003), not zoom-tier gating, marker size, or z-order.
- Re-deriving `FAME_SCORE_BOUNDS`' exact min/max/default from a full 275-entity pipeline run — the ADR explicitly accepts the 1–100/default-75 values as provisional pending a live re-tune once real scores are visible in the running app; re-tuning itself is a follow-up, not part of this implementation.
- Redirect-resolution for missing/moved Wikipedia titles in any of the 7 languages — a missing title contributes 0 pageviews for that language, per the ADR, with no fallback lookup.
- Any UI/sidebar change beyond the `FAME_SCORE_BOUNDS` numeric update — no new filter affordance, no display of the sitelinks/pageviews split to the user.
- Running the full live pipeline (`fetch`/`build-data`/`publish-data`) against real Wikidata/Wikimedia data as part of code review — that's a real network-dependent run the implementer does once the code lands, not a thing to fake or skip in tests.
